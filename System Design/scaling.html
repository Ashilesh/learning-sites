4.2

🎒Stateless servers: the secret to scaling out

If a server remembers you (your cart, your login) in its own memory, you must always go back to that server. If it dies, your cart is gone. 😢

Stateless servers keep nothing personal. Your session lives in a shared store (like Redis) or a signed token, so any server can serve anyone.

👶 Like you're 5

Instead of one waiter memorizing your order, the order is written on a shared board. Any waiter can bring your food!

4.3

🚦Load balancing — play with it!

Requests (dots) arrive at the load balancer, which picks a server. Server 4 is an old, slow machine. Try different algorithms, crank up traffic, and kill a server.

🔁 Round robin

Take turns: 1, 2, 3, 4, 1, 2… Fair if all servers are equal. Bad when one is slow.

📉 Least connections

Send to whoever is least busy right now. Adapts to slow servers & long requests.

⚖️ Weighted

Big servers get more turns. Great for mixed hardware or slowly testing a new version (canary).

#️⃣ IP / key hash

Same user → same server (sticky). Good for caches; uneven if a few users are huge.

🎲 Power of two choices

Pick 2 random servers, use the less busy one. Simple, surprisingly excellent at scale.

❤️ Health checks

The LB pings servers (“/health”) every few seconds and stops sending to ones that don't answer.

4.4

⚡Caching: remember the popular answers

A cache stores copies of answers in fast memory. Memory is ~100× faster than a database trip, so a good cache makes apps fly and protects the database.

👶 Like you're 5

Your teacher asks “what's 7 × 8?” every day. Instead of counting each time, you write 56 on a sticky note. That sticky note is a cache! 📝

Caches live at every layer, from your browser to the database

⏰ TTL (time to live) — every item expires after N seconds, so stale data fixes itself.
🕰️ LRU — kick out the oldest-used. Great default.
🔢 LFU — kick out the least-often-used. Good for stable popular items.
📥 FIFO — first in, first out. Simple but ignores popularity.

💣 Classic cache troubles

🐃 Stampede (thundering herd)

A hot key expires and 10,000 requests hit the DB at once. Fix: lock so one request refills; add random jitter to TTLs; refresh early.

👻 Penetration

Requests for things that don't exist always miss and hit the DB. Fix: cache “not found” briefly, or use a bloom filter.

🔥 Hot key

One celebrity's profile gets millions of reads, melting one cache node. Fix: replicate hot keys, add a small local cache.

🥖 Stale data

DB changed but cache still has the old value. Fix: short TTLs, delete-on-write, or change events.

🧠 Famous saying

“There are only two hard things in computer science: cache invalidation and naming things.” — Phil Karlton. Cache what is read often, changes rarely, and is OK to be a bit old.

🌐CDN: bring the files closer to people

–🐌 from origin

Light in fiber travels ~200 km per millisecond — distance is a speed limit nobody can break!

📥 Pull CDN

Edge fetches from origin on the first request, then keeps a copy (with a TTL). Easy; first user waits.

📤 Push CDN

You upload files to the CDN ahead of time. Great for big, predictable content (like a new movie).

🏷️ Cache-Control

Headers like max-age=86400 tell browsers & CDNs how long to keep a file. Put a version in file names (app.v42.js) to bust caches.

4.6

🤖Autoscaling: add servers when it's busy, remove when quiet

Traffic rises in the day and drops at night. An autoscaler watches CPU or requests and adds or removes servers. But new servers take time to boot…

🧠 Autoscaling tips

Scale on a signal that leads the pain (queue length, requests per server), keep a buffer of warm capacity, scale up fast and down slowly, and pre-scale before known events (sales, big matches).

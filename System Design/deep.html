8.1

🎟️Race conditions: two fans, one last seat

Ana and Bo click “Buy” on the last concert seat at the same moment. Pick a strategy and watch what the database does.

🔒 Pessimistic locking

“Lock first, then work.” Safe and simple, but others wait in line. Good when conflicts are common.

🔢 Optimistic locking

“Work freely, check the version at the end.” Fast when conflicts are rare; the loser retries.

⚛️ Atomic conditional write

One statement does check-and-set: UPDATE … WHERE seat_free. Often the simplest fix!

8.3

⏰Time is tricky: clocks & ordering

Every computer's clock drifts a little. Two servers can disagree by milliseconds or even seconds. So “which happened first?” using wall-clock time can be wrong!

⚠️ Last-write-wins gone wrong

Server A (clock 2 s fast) saves “x=1” at 10:00:05. Server B saves “x=2” a moment later but stamps it 10:00:04. Sorting by time keeps x=1 — the newer write is silently lost.

👶 Lamport clock = a pass-the-number game

Everyone keeps a counter. Do something → add 1. Send a note → write your counter on it. Receive a note → jump to bigger of (yours, note's) + 1. Now causes always have smaller numbers than effects!

🧮 Vector clocks

Each node keeps a counter for every node. Lets you tell “happened before” from “happened at the same time” (a conflict to merge).

🛰️ TrueTime / hybrid clocks

Some databases use GPS + atomic clocks with an uncertainty window, and simply wait it out to order transactions globally.

🔢 Sequence numbers

Often the simplest answer: let one leader hand out increasing numbers (or use a log like Kafka) instead of trusting clocks.

8.4

🗣️Gossip: spreading news like a playground rumor

No boss, no central list. Every round, each server that knows the news tells a few random others. The news reaches everyone surprisingly fast — about log(N) rounds.

Used for membership (“who's alive?”), failure detection and spreading cluster state in Cassandra, DynamoDB-style stores and Consul.

48 servers, nobody knows yet.

🧠 Failure detection

Nodes send heartbeats. Miss a few → “suspected”, miss more → “dead”. Smart detectors (phi-accrual) adapt to how jittery the network is, so a slow network doesn't trigger false alarms.

8.5

🔐Distributed locks, leases & fencing tokens

Only one worker should edit a file at a time, so they take a lock from a lock service. Locks expire (a lease) so a crashed worker can't hold them forever. But what if a worker just… freezes for a while?

🎫 Fencing token = a number that goes up every time the lock is handed out. Storage rejects writes with an older number.
🧠 Split brain = two nodes both think they're the leader. Majority votes (quorums) + fencing tokens prevent damage.
🛠️ Use proven tools like etcd or ZooKeeper for locks and leader election — this is very hard to get right yourself.
8.6

📤The dual-write problem & the outbox pattern

Saving an order to the database and publishing an “OrderPlaced” event are two separate writes. If the service crashes in between, the two worlds disagree.

📥 Outbox table

Write the business row and an outbox row in one local transaction. A relay publishes outbox rows later — guaranteed, never lost.

📜 CDC (change data capture)

Tools like Debezium read the database's own change log and turn every change into an event stream — no extra code in the app.

🔁 Consumers must be idempotent

Relays may publish an event twice after a crash. Consumers skip IDs they've already processed.

🧮 G-Counter CRDT: each device counts its own likes; merge = take the max per device, total = sum. Never loses a like!
📝 Collaborative docs (Google Docs, Figma, Notion) use CRDTs or Operational Transformation (OT) so everyone's typing merges sensibly.
⚖️ Trade-off: CRDTs need extra metadata and only some data types merge nicely; “last write wins” is simpler but drops changes.
8.8

🎲HyperLogLog: count millions of visitors in a few hundred bytes

Counting unique visitors exactly means remembering every ID — gigabytes. HyperLogLog estimates it with a tiny memory and ~3% error.

👶 The coin-flip trick

If someone says “my longest streak was 10 heads in a row”, they probably flipped about 2¹⁰ ≈ 1,000 times. HyperLogLog hashes each visitor to random bits and remembers only the longest streak of zeros it has seen (in many small buckets, then averages).

📊 Count-Min Sketch: approximate “how often?” counts — find heavy hitters / top-K trending hashtags in tiny memory.
🌸 Bloom filter: “definitely not / maybe” membership (see Advanced Patterns).

Tap each milestone. The times are a guide for a 45-minute interview; for a real project each step might take days.

11.2

❓Great questions to ask first

👥 Who are the users and how many (daily / at peak)?
🎯 Which 2–3 features matter most? What's out of scope?
👀 More reads or more writes? By how much?
⚡ How fast must it feel? (p99 target)
🟢 How bad is downtime? (availability target)
🎯 Is slightly stale data OK? Where must it be exact?
🌍 One country or worldwide? Any data-location laws?
💾 How long do we keep data? How big is each item?
🔐 What's sensitive (payments, health, kids' data)?
💰 Any budget, team-size or timeline limits?
11.3

📄The design document template

A design doc lets your team review the idea before building it — catching problems when they cost an eraser, not a rewrite. Open each section to see what goes in it.

📋 Grab it

Paste into Google Docs, Notion, Confluence or a GitHub README.

11.4

🖍️Drawing diagrams people understand

➡️ Flow left to right

Users on the left, data stores on the right. Readers follow the request like a story.

🏷️ Label every arrow

“HTTPS”, “publishes OrderPlaced”, “reads profile”. An unlabeled arrow means nothing.

🎨 Style = meaning

Solid = synchronous call, dashed = async/event. Same color for the same kind of box.

🔢 Number the steps

For a key flow, put ①②③ on arrows so the walk-through is obvious.

📏 Add numbers

QPS on arrows, sizes on stores. Numbers turn a picture into a design.

🔍 One question per diagram

High-level overview first, then zoom-in diagrams for each deep dive.

11.5

🔍Questions reviewers will ask (ask them yourself first!)

💥 What happens when each box dies?
📈 What breaks first at 10× traffic?
⏱️ What's the p99 of the main flow?
🎯 Where is the single point of failure?
🔁 Are retries safe (idempotent)?
🔙 How do we roll back?
📊 How do we know it's healthy?
🔐 What data could leak, and to whom?
💰 What does it cost per month?
🧹 What's the simplest version that works?

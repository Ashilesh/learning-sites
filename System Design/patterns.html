6.1

📮Synchronous vs asynchronous

📞 Synchronous = a phone call

You ask and wait on the line until you get the answer. Simple, but if the other side is slow or down, you're stuck too.

💌 Asynchronous = a text message

You send it and go on with your day. The other side handles it when ready. Survives spikes and outages!

6.2

📬Message queues absorb the rush

Orders pour in (producers). Workers process them (consumers). The queue in the middle is a buffer — like a ticket rail in a busy kitchen. Hit Spike! and watch it soak up the rush.

🔗 Decoupling

Producers don't need to know who processes the job, or if they're even online.

🪣 Load leveling

Spikes become a longer line, not a crash. Workers chew through at a steady pace.

☠️ Dead-letter queue

Jobs that keep failing get parked in a DLQ for humans to inspect, instead of blocking the line.

🛑 Backpressure

If the queue grows forever, tell producers to slow down (or shed load). A queue hides problems — watch its length!

6.3

📢Queue vs Pub/Sub vs Event stream

📬 Queue

Each message goes to one worker. Splits the work.

📢 Pub/Sub

Each message goes to every subscriber. Like a group chat.

📜 Event stream (log)

An append-only diary. Readers keep a bookmark (offset) and can replay history.

🧠 Event streams (Kafka-style)

Messages are kept for days and split into partitions (lanes). Order is guaranteed within a partition, so use a key like user_id to keep one user's events in order. Many teams can read the same stream independently.

6.4

🛗Delivery guarantees & idempotency

🎯 At-most-once

Send once, never retry. Might get lost. OK for metrics.

🔁 At-least-once

Retry until acknowledged. Never lost, but might arrive twice. The most common!

💎 Exactly-once

Really = at-least-once + idempotent processing (duplicates have no effect).

Idempotent = doing it twice has the same effect as doing it once.

👶 Like you're 5

Pressing the elevator button 10 times still calls one elevator 🛗. “Set volume to 5” is idempotent; “turn volume up by 1” is not.

Trick: the client sends a unique idempotency key. The server remembers keys it has seen and ignores repeats.

6.5

🏘️Monolith vs Microservices

🏰 Monolith: one big app, one deploy, one database

🏘️ Microservices: small apps, each owns its data

🏰 Monolith🏘️ Microservices
Start-up speed✅ Fast & simple🐢 Lots of setup
TeamsGets crowded with 50+ engineers✅ Teams own & ship services independently
ScalingScale everything together✅ Scale only the busy part
FailuresOne bug can take down everythingIsolated… but network calls fail in new ways
Debugging✅ One place, one stack traceNeeds tracing across many services
Data✅ Easy transactions & JOINsEach service owns its DB → sagas, events
🧠 The wise path

Start with a modular monolith (clean modules inside one app). Split a module into a service only when a team or scaling need clearly demands it. A “distributed monolith” (services that must deploy together) is the worst of both worlds.

Gateway at the front door, a registry so services find each other, and sidecar proxies (a “service mesh”) handling retries, TLS and metrics

6.6

🗳️Consensus: how machines agree (Raft)

5 servers must agree on one leader who orders all writes. The leader sends heartbeats 💓. If followers stop hearing them, someone becomes a candidate and asks for votes. A majority (3 of 5) wins!

👶 Like you're 5

The class captain keeps saying “I'm here!”. If the captain goes home sick, the first kid who notices says “Vote for me!”. Get most of the class's votes → new captain.

Used inside etcd, Consul, CockroachDB, Kafka (KRaft) and more. A majority means the cluster survives 2 of 5 machines failing.

Leader is sending heartbeats 💓

6.7

🧳Distributed transactions: 2PC vs Sagas

Booking a trip needs a flight, a hotel and a car — three different services with their own databases. What if the car fails after the flight is booked?

🤝 Two-phase commit (2PC)

A coordinator asks everyone “Ready?” (prepare). Only if all say yes, it says “Commit!”.

all-or-nothingslow, locks heldcoordinator dies = everyone stuck

🧳 Saga

Do each step for real, one by one. If a step fails, run compensating steps to undo the earlier ones (cancel the hotel, refund the flight).

no global locksscalesbriefly inconsistentmust design “undo”s

6.8

📒Event sourcing & CQRS

📒 Event sourcing: keep the diary, not just the total

Instead of storing “balance = $70”, store every event. The balance is computed by replaying them. You get a perfect history & time travel!

Balance:$0

CQRS: separate the write model from the read models

🧠 Why split reads and writes?

Writes need rules and validation; reads need speed and many shapes (search, dashboards, feeds). Events flow from the write side to build fast read views — at the cost of a short delay (eventual consistency).

6.9

🌸Bloom filter: a tiny memory that says “definitely not” or “maybe”

A row of light switches (bits). Adding a word flips 3 switches chosen by 3 hash functions. Checking a word looks at its 3 switches: if any is off → definitely not seen. All on → probably seen.

Used to skip useless disk reads in databases, check “is this username taken?”, avoid showing you the same post twice, and block known-bad URLs — using very little memory.

⚠️ The catch

False positives can happen (switches turned on by other words), but never false negatives. You also can't delete items easily.

Add a few words, then check some others!

6.11

🏭Batch vs stream processing

🧺 Batch

Collect a big pile, process it all at once (every night). Like doing laundry once a week.

Reports, billing, ML training. Tools: Spark, MapReduce, dbt.

🚰 Stream

Process each event the moment it arrives. Like washing each dish right after using it.

Fraud detection, live dashboards, alerts. Tools: Flink, Kafka Streams.

🗺️ MapReduce in one line

Map: many workers each count words in their own pages. Reduce: add up the counts per word. Split → work in parallel → combine.

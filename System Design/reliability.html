7.1

💥The many ways things fail

💾

Hardware

Disks, memory and power supplies wear out. With 10,000 machines, something breaks every day.
🐛

Bugs

A bad deploy, a memory leak, a leap-second surprise.
🌐

Network

Packets lost, slow links, a cut cable, DNS gone wrong.
🙈

Humans

A typo in a config is one of the most common causes of big outages.
🌊

Overload

A viral post or a sale: 50× normal traffic in minutes.
🔗

Dependencies

A payment provider or cloud service you rely on goes down.
🧠 The goal

Remove single points of failure (SPOF): anything that, if it breaks alone, breaks everything. Ask of every box in your diagram: “what if this dies right now?”

7.2

🔁Redundancy & failover

🧍‍♂️🧍 Active–passive

A standby waits, copying data. If the main one dies, the standby takes over. Simple; the standby sits idle.

🧍🧍 Active–active

All copies serve traffic all the time. Better use of money and instant failover; harder to keep data in sync.

👶 Like you're 5

A plane has two engines. If one stops, the other keeps it flying until landing. ✈️

7.3

⏳Timeouts, retries, backoff & jitter

⏰ Always set a timeout

Never wait forever. A stuck call holds threads, memory and connections until everything jams.

🔁 Retry… carefully

Retry only temporary errors (timeouts, 503), only safe (idempotent) operations, with a limit.

📈 Backoff + 🎲 jitter

Wait longer each time (1s, 2s, 4s…) and add randomness so clients don't all retry at the same instant.

7.4

🔌Circuit breaker: stop calling a broken friend

Like the breaker in your house: if a service keeps failing, trip the breaker and fail fast for a while instead of piling up slow, doomed calls. Then carefully test if it's healthy again.

  • 🟢 Closed: calls flow normally; count failures.
  • 🔴 Open: too many failures → reject instantly (use a fallback).
  • 🟡 Half-open: after a cool-down, let one trial call through. Success → close. Fail → open again.

7.5

🪣Rate limiting: the token bucket

Protect your service from floods (and unfair users). A bucket holds tokens that drip in at a steady rate. Each request takes a token. Empty bucket → 429 Too Many Requests.

The bucket size allows short bursts, the drip rate sets the long-term limit.

7.6

🚢Bulkheads, graceful degradation & load shedding

🚢

Bulkheads

Ships have walls inside so one leak doesn't sink the ship. Give each dependency its own pool of threads/connections, so a slow one can't eat them all.

🪫

Graceful degradation

If recommendations are down, show “popular items” instead of an error page. Keep the core working (play the video!), drop the extras.

🧯

Load shedding

When overloaded, quickly reject some low-priority requests so the important ones (checkout!) still succeed.

🐒

Chaos engineering

Break things on purpose (kill servers, add latency) in a controlled way to prove your system survives — before real life tests it for you.

7.7

🌪️Disaster recovery: RPO & RTO

⏪ RPO — Recovery Point Objective

How much data can you afford to lose? “At most 5 minutes of orders.” → back up / replicate at least that often.

⏩ RTO — Recovery Time Objective

How long can you be down? “Back within 1 hour.” → practice restoring that fast.

The DR ladder: more money → faster recovery

🧊 Backup & restoreCopies saved elsewhere; rebuild from scratch.⏱️ hours–days💰
🔥 Pilot lightData replicated, minimal core running, scale up when needed.⏱️ ~hour💰💰
♨️ Warm standbyA smaller full copy always running in another region.⏱️ minutes💰💰💰
🌍 Multi-site active–activeEvery region serves live traffic.⏱️ ~0💰💰💰💰
⚠️ The 3-2-1 backup rule

Keep 3 copies, on 2 different kinds of storage, with 1 off-site. And test restores — a backup you've never restored is just a hope.

7.8

🚀Shipping changes safely

🎢 Rolling

Replace servers a few at a time.

🔵🟢 Blue–green

Two full copies; flip traffic at once, flip back if bad.

🐤 Canary

Send 5% to the new version, watch metrics, then grow.

🧠 Also

Feature flags let you turn features on/off without deploying. Make database changes backward compatible (expand → migrate → contract) so old and new code can run side by side. Automate rollback.

7.9

🔭Observability: seeing inside your system

📈

Metrics

Numbers over time: requests/sec, error %, p99 latency, CPU. Cheap; great for dashboards & alerts.

📜

Logs

Diary lines of what happened: “order 42 failed: card declined”. Use structured (JSON) logs with request IDs.

🧵

Traces

Follow ONE request through every service and see where the time went (below ↓).

A trace waterfall: the request spent most of its time in the slow DB query → fix that first!

🚦 The four golden signals

⏱️Latency
how long (watch p99!)
🚗Traffic
how much demand
💥Errors
how many fail
🧃Saturation
how full (CPU, memory, queues)
🧠 Alerting that people trust

Alert on symptoms users feel (SLO burn rate, error spikes), not every CPU blip. Every alert should be actionable and link to a runbook. Too many alerts → people ignore them all.

7.10

🔐Security: defense in depth

Like a castle: many walls, so one breach isn't game over

🪪 Authentication vs 🎟️ Authorization

AuthN = who are you? (show your ID card). AuthZ = what may you do? (does your ticket let you into the VIP room?).

🗝️ OAuth = a valet key

Give an app a limited key (“read my photos”) instead of your password — like a car valet key that can't open the trunk.

🎫 JWT: a signed wristband

header · payload (who + role) · signature. Anyone can read it, nobody can fake it without the secret. Keep it short-lived!

🔒 Encrypt in transit (TLS everywhere) and at rest (disks, backups).
🤏 Least privilege — every service/person gets only the access it needs.
🧼 Validate input — never trust it (SQL injection, XSS). Use parameterized queries.
🗝️ Secrets in a vault, never in code. Rotate keys regularly.
🛡️ WAF + DDoS protection at the edge; rate limit login attempts.
📋 Audit logs of who did what. Patch dependencies quickly.

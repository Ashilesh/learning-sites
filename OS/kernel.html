Chapter 7

Kernel, Syscalls & Devices ⚙️

The kernel is the heart of the OS: the one program trusted to touch the hardware. Let's see how apps talk to it, how hardware gets its attention, and how it's built.

🧸 In one sentence: the kernel is like a bank vault with a teller window 🏦 — you can't walk into the vault, but you can ask the teller (a system call), and the alarm bell (an interrupt) can always get the teller's attention.

🛡️ Two modes: user and kernel

🧸 Kid version

The CPU has a grown-up mode and a kid mode. Apps always run in kid mode: they can do math and use their own memory, but can't touch the hardware or other apps' stuff. Only the kernel runs in grown-up mode.

🐧 In Linux (x86)

The CPU has 4 privilege rings, but Linux uses only two: ring 0 (kernel mode) and ring 3 (user mode). ARM calls them exception levels (EL1 kernel, EL0 user). Forbidden instructions in ring 3 cause a trap → the kernel usually kills the app.

$ time ls > /dev/null
real  0m0.003s
user  0m0.001s     # time spent in user mode
sys   0m0.002s     # time spent in the kernel for us

🔬 Deep dive: making system calls cheaper
  • vDSO: some calls like clock_gettime() don't even enter the kernel — the kernel maps a tiny read-only page of code+data into every process.
  • Buffering: glibc's printf collects text and calls write() once per line/buffer instead of per character.
  • io_uring (since 5.1): apps put many I/O requests into a shared ring buffer; the kernel picks them up in batches — very few system calls for lots of I/O.
  • eBPF: safe little programs you load into the kernel to filter packets, trace events or enforce security — without writing a kernel module.

🔔 Interrupts: the doorbell

🚪👀

Polling

Walk to the door every 10 seconds to check for a visitor. Wastes your time.

CPU keeps asking the device "done yet?"

🔔

Interrupts

Get on with life; the doorbell rings when someone arrives.

Device signals the CPU when it needs attention.

📦🤖

DMA

The delivery robot carries the boxes inside itself and only rings to say "done!".

Device copies data straight into RAM, then interrupts.

$ cat /proc/interrupts | head -5
           CPU0     CPU1     CPU2     CPU3
  1:      9921        0        0        0  IO-APIC  1-edge   i8042
  8:         0        0        0        1  IO-APIC  8-edge   rtc0
128:         0   448113        0        0  PCI-MSIX nvme0q1
131:    211534        0     4212        0  PCI-MSIX eth0-rx-0
🐧 Top half & bottom half

Interrupt handlers must be super quick (other interrupts may be waiting!). So Linux splits work: the top half grabs the data and says "got it", and the slower bottom half (softirqs, tasklets, workqueues, threaded IRQs) finishes later. Under heavy network load, Linux switches from interrupts to polling (NAPI) — the best of both.

🔌 Drivers & kernel modules

🧸 Translators

Every printer, Wi-Fi chip and graphics card speaks its own secret language. A driver is a translator that knows that language and offers a standard one to the rest of the kernel. Most of Linux's code is drivers!

🐧 Loadable modules

Drivers can be compiled into the kernel or loaded later as modules (.ko files in /lib/modules/$(uname -r)/). udev loads the right module automatically when hardware appears.

$ lsmod | head -4
Module                  Size  Used by
nvme                   61440  3
iwlwifi               622592  1 iwlmvm
snd_hda_intel          61440  4
$ lspci -k | grep -A2 -i ethernet

#include <linux/module.h>
#include <linux/init.h>

static int __init hello_init(void) {
    pr_info("hello: the kernel says hi! 👋\n");
    return 0;
}
static void __exit hello_exit(void) {
    pr_info("hello: bye!\n");
}
module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
# build with a tiny Makefile, then:  sudo insmod hello.ko ; sudo dmesg | tail -1
⚠️ With great power…

A module runs in ring 0 with full power. A bug in a driver can crash the whole machine (a kernel panic, or an "oops"). That's the main argument for microkernels — next section.

🏗️ How kernels are built: three designs

Monolithic Linux

Everything (scheduler, memory, file systems, network, drivers) in one big kernel program.

✅ fast: parts call each other directly
⚠️ one buggy driver can crash it all

Microkernel MINIX, seL4, QNX

A tiny kernel does just the basics; drivers and file systems run as separate user-space servers.

✅ crash-proof & secure (a driver can restart)
⚠️ slower: lots of messages (IPC)

Hybrid Windows NT, macOS XNU

Microkernel ideas, but performance-critical parts moved back into kernel space.

✅ a pragmatic middle ground
⚠️ "a monolith with good manners" — critics

🥊 The famous debate (1992)

Professor Andrew Tanenbaum (creator of MINIX) told young Linus Torvalds that monolithic kernels were obsolete. Linus disagreed. Decades later: Linux (monolithic, but modular) runs most of the world, while microkernels shine where safety is everything — cars, planes, phones' secure chips (seL4 is even mathematically proven correct!).

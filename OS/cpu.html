Chapter 4

How the CPU Runs Code 🔁

Every program — a game, a browser, Linux itself — is just a long list of tiny instructions. The CPU reads them and does them, one after another, billions of times a second. But who hands the CPU those instructions? The OS? Not quite… 🤔

🧸 In one sentence: the CPU is a super-fast chef reading a recipe one line at a time 👩‍🍳 — a bookmark called the program counter remembers which line is next. The OS is the head chef who puts the recipe on the stand and rings a bell ⏰ when it's someone else's turn.

🧩 What is an instruction?

You write code in a language for humans. A compiler turns it into tiny commands the CPU understands — machine code: just numbers (bytes) in memory.

🧸 Tiny, tiny steps

A CPU can't "make a game". It can only do baby steps: copy a number, add two numbers, compare, jump to another line. Billions of baby steps per second add up to everything you see on screen. 🐜🐜🐜

$ objdump -d --no-show-raw-insn /usr/bin/ls | sed -n '8,12p'
    6ab0:  endbr64
    6ab4:  xor    ebp,ebp
    6ab6:  mov    r9,rdx
    6ab9:  pop    rsi
    6aba:  mov    rdx,rsp
# 6ab0 is ls's very first instruction: its "entry point"

🔁 The heartbeat: fetch → decode → execute

🔎

1. Fetch

Read the instruction at the address in the program counter (on x86-64 it's called RIP). Move the counter to the next one.

🧩

2. Decode

The control unit figures out what the bytes mean: "ah, add these two".

⚙️

3. Execute

The ALU (math unit) does it, or memory is read/written, or the program counter jumps somewhere else.

💡 That's all a CPU ever does

Fetch, decode, execute, repeat — from the moment it powers on (starting at the reset vector in the firmware, Chapter 2) until it's switched off. A 4 GHz CPU ticks 4 billion times per second, and modern cores finish several instructions per tick.

👑 So… does the OS fetch the instructions?

🧸 The teacher and the worksheet

No! The OS is like a teacher: it hands a kid (the CPU) a worksheet (the program), points to the first question (sets the program counter) and sets a kitchen timer ⏰. The kid does every question alone, super fast. The teacher only comes back when the timer rings, when the kid raises a hand (a system call), or when something goes wrong (a fault).

🐧 Why it must be this way

If the kernel had to hand over each instruction, every instruction would cost hundreds of extra instructions — your computer would be 100× slower. So the CPU fetches on its own, and hardware (the MMU) checks every single access against the page tables the kernel prepared. The kernel sets the rules once; the hardware enforces them billions of times per second.

🔔 The 4 ways the kernel gets the CPU back

⏰

Timer interrupt

A hardware timer rings every few milliseconds. That's how Linux stops endless loops from freezing your computer.

🚪

System call

The program asks for help (read, write, exit…) with the syscall instruction.

💥

Exception / fault

Page fault, divide by zero, illegal instruction. The CPU jumps to the kernel to fix it — or to stop the program.

🔔

Device interrupt

A key was pressed, a disk read finished, a network packet arrived.

🏎️ Going faster: the pipeline

🧺 The laundry trick

Washing, drying and folding one load before starting the next is slow. Smart way: while load 1 is drying, load 2 is already washing! CPUs do the same with instructions — each step (fetch, decode, execute…) works on a different instruction at the same time.

cycles: –
F fetchD decodeE executeM memoryW write back

🏭 The pipeline factory (3D)

🔮 Branch prediction

At an if, the CPU guesses which way the program will go and starts fetching from there before it knows. Modern guessers are right ~95%+ of the time. A wrong guess = throw away the work (a "branch miss").

🔀 Out-of-order

If an instruction is waiting for slow memory, the CPU runs later, independent instructions first — then puts the results back in the right order.

🛣️ Superscalar

Several pipelines side by side: a modern core can start 4–8 instructions per cycle.

🔬 Deep dive: when guessing goes wrong — Spectre & Meltdown

In 2018, researchers showed that work done on a wrong guess (speculative execution) leaves traces in the caches that a clever program can measure to read secrets. Linux added mitigations, like KPTI (separate page tables for kernel and user) and retpolines. You can see which ones your machine uses:

$ grep . /sys/devices/system/cpu/vulnerabilities/* | cut -d/ -f7
meltdown:Not affected
spectre_v1:Mitigation: usercopy/swapgs barriers and __user pointer sanitization
spectre_v2:Mitigation: Enhanced / Automatic IBRS; IBPB: conditional
$ perf stat -e cycles,instructions,branch-misses ls > /dev/null
     2,114,903  cycles
     2,843,107  instructions      #  1.34  insn per cycle
        16,032  branch-misses

⚡ Caches: keeping instructions close

RAM is ~100× slower than the CPU. So every core has small, super-fast caches. Instructions travel from RAM in chunks of 64 bytes (a "cache line") and land in a special L1 instruction cache.

$ lscpu | grep -i cache
L1d cache:   256 KiB (8 instances)
L1i cache:   256 KiB (8 instances)
L2 cache:    8 MiB (8 instances)
L3 cache:    16 MiB (1 instance)
$ getconf LEVEL1_DCACHE_LINESIZE
64
💡 Why loops are fast

Code runs mostly in order, and loops repeat the same few instructions. After the first trip, they're already in L1 — the CPU hardly ever waits. Programmers call this locality. (Memory hierarchy with real speeds → Chapter 5.)

🧝 ELF: how Linux stores programs

Linux programs are ELF files (Executable and Linkable Format). Inside: a header ("I'm for x86-64, start at address 0x6ab0"), segments to map into memory (code = read+execute, data = read+write), and the name of a helper — the dynamic loader ld-linux.so, which runs first to hook up shared libraries like libc.

🧸 A recipe book with a table of contents

The header is the table of contents: "recipes start on page 6ab0". execve() reads it and tells the CPU where to start.

$ file /usr/bin/ls

🌍 CPUs speak different languages

x86-64

Intel & AMD PCs and servers. Instructions are 1–15 bytes long (CISC).

uname -m → x86_64

ARM64 (AArch64)

Phones, Apple M-chips, Raspberry Pi, many cloud servers. Every instruction is 4 bytes (RISC).

uname -m → aarch64

RISC-V

An open, free instruction set anyone can build. Growing fast in boards and chips.

uname -m → riscv64

🐧 One kernel, many CPUs

Linux runs on all of them. CPU-specific code lives in arch/x86, arch/arm64, arch/riscv…; everything else is shared. A program must be compiled for your CPU's language — that's why downloads say "x86_64" or "arm64".

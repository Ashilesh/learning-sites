Chapter 10

Containers & Docker 📦

Docker feels like magic: a whole "mini computer" starts in under a second. The secret? There's no mini computer. A container is a normal Linux process wearing three gadgets: namespaces, cgroups and a layered file system.

🧸 In one sentence: containers are like apartments 🏢 in one building — everyone shares the same foundation and plumbing (the kernel), but each apartment has its own walls and door (namespaces), its own water & power limit (cgroups), and furniture from a stack of see-through catalogs (image layers).

🧐 A container is just a process

$ docker run -d --name web nginx
$ docker top web                     # processes inside, as the HOST sees them
UID    PID     PPID   CMD
root   4123    4101   nginx: master process
101    4150    4123   nginx: worker process
$ ps -p 4123 -o pid,comm             # it's right there in the host's ps!
    PID COMMAND
   4123 nginx
$ sudo ls -l /proc/4123/ns | head -4  # …with its own namespaces
lrwxrwxrwx  ipc -> 'ipc:[4026532771]'
lrwxrwxrwx  mnt -> 'mnt:[4026532769]'

🐧 Linux does both!

KVM is built into the Linux kernel: it turns Linux into a hypervisor (/dev/kvm). And "Docker Desktop" on Mac/Windows secretly runs a small Linux VM, because containers need a Linux kernel. Cloud services even mix them: tiny "micro-VMs" (like Firecracker) give each container its own kernel for extra safety.

🦮 Gadget 2: cgroups (what you can USE)

🧸 Allowance

Namespaces hide things, but a hidden greedy process could still eat all the CPU and RAM. Control groups give each group of processes an allowance: "you get half a CPU and 256 MB, no more."

🐧 It's files, of course

cgroups v2 lives at /sys/fs/cgroup. Each folder is a group; write numbers into files like cpu.max, memory.max, pids.max, io.max. Docker and systemd just create folders and write files!

🦮 cgroups simulator

host: 4 CPUs · 4 GB RAM
$ docker run -d --name db --memory=512m --cpus=1.5 --pids-limit=200 postgres
$ cat /sys/fs/cgroup/system.slice/docker-3f2a….scope/memory.max
536870912
$ cat /sys/fs/cgroup/system.slice/docker-3f2a….scope/cpu.max
150000 100000          # 150 ms of CPU time every 100 ms = 1.5 CPUs
$ systemd-cgls | head -5    # the whole cgroup tree

🥞 Gadget 3: image layers (OverlayFS)

🧸 Stacked see-through sheets

Imagine drawing on stacked transparent sheets. Looking from the top, you see all the drawings combined. Bottom sheets are locked (read-only, shared by everyone). Each container gets one fresh top sheet to scribble on. Want to "change" a locked drawing? Copy it up to your sheet and change the copy!

FROM ubuntu:24.04                   # layer 1: base OS files
RUN apt-get install -y python3      # layer 2: + python
COPY app.py config.yml /app/        # layer 3: + your code
CMD ["python3", "/app/app.py"]      # metadata only, no layer
$ docker history myapp:1.0          # see the layers
$ docker info | grep Storage
 Storage Driver: overlay2

⚠️ The container layer is temporary!

When the container is removed, its writable layer is deleted. Store anything important (databases, uploads) in a volume (-v dbdata:/var/lib/postgresql/data), which lives outside the layers.

✅ Container best practices

🪶 Small images

Use slim/alpine/distroless bases and multi-stage builds. Less stuff = faster pulls, fewer security holes.

🙅 Don't run as root

USER 1000 in the Dockerfile, or rootless Docker/Podman with user namespaces.

🦮 Always set limits

--memory, --cpus, --pids-limit. One leaky container shouldn't sink the host.

🧱 Drop what you don't need

--cap-drop=ALL, keep the default seccomp profile, --read-only root FS, never --privileged casually.

💾 Data in volumes

Containers are cattle, not pets: they can be deleted anytime. Keep state in volumes or databases.

📌 Pin versions

postgres:16.4 not postgres:latest. Same image → same behavior, every time.

1️⃣ One job per container

One main process (PID 1) per container. Make sure it handles SIGTERM, or use --init.

🩺 Health checks & logs

Add HEALTHCHECK; log to stdout/stderr so docker logs works.

☸️ At scale: Kubernetes

Orchestrates thousands of containers across many machines — still using the same namespaces & cgroups (via containerd or CRI-O).

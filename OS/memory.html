Chapter 5

Memory, RAM & VRAM 🧮

Every running program needs memory. There's never enough of the fast kind. The OS plays a clever game of musical chairs — and lies to every program about how much it has. 🤫

🧸 In one sentence: RAM is your desk (small, fast, cleared every night), the disk is the bookshelf (big, slow, permanent), and the OS is the librarian who decides which books sit on the desk.

🏔️ Fast and small vs big and slow

Computer memory comes in layers. Click a layer — the times are scaled up so that 1 nanosecond = 1 second.

🤯 Why it matters

If the CPU had to wait for the SSD on every step, a 1-second job would take days. So the OS keeps hot data in RAM and the CPU keeps the hottest data in its caches. Most of memory management is about guessing what you'll need next.

🪄 Virtual memory: the great illusion

🧸 Every kid gets a "whole house"

Each program is told: "You own the whole house! Rooms 0 to a zillion!" But really, the OS secretly maps each of its rooms to a real room somewhere in the hotel (RAM) — or to the storage shed (disk). Programs can't even name another program's rooms, so they can't mess with them. 🔒

🐧 In Linux

Memory is cut into pages (4 KB). Each process has a page table that maps its virtual pages → physical frames. The CPU's MMU chip does the translation on every memory access. On x86-64, page tables have 4 levels (5 on huge servers).

🗺️ What's inside a process's memory

📜 text

The program's machine code. Read-only + executable.

📦 data & bss

Global variables (initialized / zero-filled).

⛰️ heap ↑

malloc() memory. Grows up via brk() or mmap().

📚 mmap area

Shared libraries (libc.so), mapped files.

🥞 stack ↓

Function calls & local variables. Grows down. Too deep → stack overflow!

👑 kernel

Mapped in every process, but locked: touching it from user mode = crash.

🔬 Deep dive: real x86-64 page tables

A real 48-bit virtual address is split into 5 parts: four 9-bit indexes (PGD → PUD → PMD → PTE) and a 12-bit offset. Each level is a 4 KB table of 512 entries. A TLB miss means up to 4 memory reads just to find one address — that's why the TLB matters so much. Huge pages (2 MB or 1 GB) skip levels and cover more memory per TLB entry: great for databases. Linux can do this automatically with Transparent Huge Pages.

$ cat /sys/kernel/mm/transparent_hugepage/enabled
always [madvise] never
$ grep -i huge /proc/meminfo | head -3

💥 Page faults, step by step

🧸 "That page isn't on my desk!"

You open your book to page 57 — but it's not on your desk. Maybe it's on the shelf behind you (quick: minor fault). Maybe it's at the library across town (slow: major fault). Or maybe page 57 doesn't exist at all (😱 segmentation fault). The librarian (the kernel) sorts it out while you wait.

🐧 Not an error — mostly!

A page fault is the CPU saying "I can't use this address right now, kernel please help". Linux uses them on purpose for lazy allocation, loading programs, swap and copy-on-write. Only a fault on an address the program doesn't own becomes a crash.

🔬 Deep dive: what the CPU and Linux actually do
  • The CPU raises exception 14 (#PF) on x86, saving the faulting address in register CR2 and an error code (read/write? user/kernel? present?).
  • Linux's exc_page_fault() → handle_mm_fault() finds the VMA (the process's list of valid regions, the lines in /proc/PID/maps) containing the address.
  • No VMA, or the access breaks its permissions → SIGSEGV. Otherwise it fills the page-table entry (anonymous zero page, page-cache page, swap-in, or COW copy).
  • Returning from the exception re-runs the same instruction, which now succeeds. The program never notices — except for the time it took.
  • Major faults can be avoided for important programs with mlock(), prefetching (madvise(MADV_WILLNEED)), or enough RAM so nothing is swapped.

🧸 Only 3 seats at the table

Pages keep arriving and there are only a few seats (frames). When someone new comes and all seats are full, someone has to leave. Who? The one who came first (FIFO)? The one who hasn't been used for the longest (LRU)? Or the one who won't be needed for the longest time — if you could see the future (OPT)?

🐧 What Linux does

True LRU is too expensive to track for millions of pages, so Linux approximates it with active and inactive lists (and, since 6.1, the multi-gen LRU). The CPU sets an "accessed" bit when a page is touched; the kernel checks these bits to see what's hot. 🌡️

📄 Page cache

"Free RAM is wasted RAM." Linux fills spare RAM with copies of files you read. That's the buff/cache column — it's given back instantly when apps need it.

💤 Swap

When RAM is tight, rarely-used app pages are written to disk. Slow to bring back, but better than crashing. vm.swappiness (default 60) tunes how eager Linux is.

💥 OOM killer

Out of RAM and swap? Linux kills the process with the highest oom_score (mostly: the biggest). Protect important ones with oom_score_adj.

🤔 Wait — Linux promises more memory than it has?

Yes! Overcommit: malloc(1 GB) usually succeeds instantly because Linux only hands out real frames when pages are first touched (demand paging). Most programs never touch everything they ask for. The OOM killer is the price of this optimism. (vm.overcommit_memory = 0 heuristic, 1 always, 2 strict.)

🐄 Copy-on-write: why fork() is cheap

Copying a 2 GB process on every fork() would be slow. Linux cheats — beautifully.

🧱 Inside the kernel: the buddy allocator

🧸 Chocolate bar splitting

The kernel keeps free memory in chunks of 1, 2, 4, 8, 16… pages. Need 2 pages but only have a 16? Snap it in half (8+8), half again (4+4), again (2+2) → take one 2. When you give it back, it re-joins its "buddy" half to make big pieces again. 🍫

🐧 Two-level allocation

Buddy allocator: hands out whole pages in power-of-two blocks (see /proc/buddyinfo). SLUB allocator: carves pages into small, same-sized objects (inodes, task_structs…) — see slabtop. User programs use malloc() in glibc on top of brk/mmap.

🔬 How RAM chips really work

🧸 Millions of leaky buckets

A RAM chip is a giant grid of microscopic buckets (capacitors) that hold a tiny bit of electricity. Full bucket = 1, empty = 0. But the buckets leak! So the memory controller refills every bucket about 16 times a second (refresh). Switch the power off and they all drain — that's why RAM forgets everything. 🪣💧

🔧 The real numbers
  • 1 bit = 1 transistor (the tap) + 1 capacitor (the bucket): that's DRAM.
  • Cells are arranged in rows × columns inside banks; a read opens a whole row into the "row buffer".
  • Every row must be refreshed within 64 ms.
  • A DDR5 stick has 8–16 chips; two channels give ~60–90 GB/s.
  • CPU caches use SRAM: 6 transistors per bit, no leaking, much faster — but big and expensive.

🪣 A tiny DRAM chip (8 rows × 16 bits)

refresh: on

Turn auto-refresh off and wait a few seconds: the buckets leak until 1s read back as 0s. Real chips leak far more slowly (milliseconds), but the idea is the same.

🔬 Deep dive: Rowhammer — when buckets disturb their neighbours

Opening one DRAM row again and again, very fast, can leak charge into the neighbouring rows and flip their bits — even rows belonging to other programs or the kernel. This "Rowhammer" effect has been used in real attacks. Defences: ECC memory, more frequent refresh, and in-chip "target row refresh". A great example of hardware physics becoming an OS security problem!

🎨 RAM vs VRAM: two kinds of fast memory

🧸 The kitchen and the artist's palette

RAM is the big kitchen counter everyone uses. VRAM (video RAM) is the artist's own paint palette, glued right next to the easel (the GPU). The artist paints super fast from the palette — but new paint first has to be carried down the hallway (the PCIe bus) from the kitchen. 🎨🏃

🐧 Who manages what

The kernel's memory manager (this whole chapter) manages RAM. VRAM is managed by the GPU driver (amdgpu, i915/xe, nouveau or NVIDIA's) through the kernel's DRM graphics layer: it hands out "buffer objects", gives the GPU its own page tables, and can even move buffers from VRAM back to RAM when VRAM is full.

🎮

Dedicated GPU

Its own VRAM on the card. Data is copied RAM → VRAM over PCIe by the GPU's DMA engine. Fastest for games and AI.

💻

Integrated GPU

No VRAM at all! The GPU inside the CPU shares normal RAM. The firmware may reserve a slice ("UMA frame buffer"), so free shows a bit less RAM.

🍏

Unified memory

Apple M-chips and game consoles: one big fast pool used by CPU and GPU together — no copying needed.

🖼️ How much VRAM does one picture need?

Each pixel = 4 bytes (red, green, blue, alpha). The GPU draws the next frame into a "back buffer" while the screen shows the "front buffer", then they swap — so you never see half-drawn pictures.

🔬 Deep dive: GPUs have page tables and page faults too
  • Modern GPUs have their own MMU: each app gets a GPU virtual address space, managed by the driver — just like a process gets one on the CPU.
  • When VRAM is full, the driver (via TTM) evicts buffers to system RAM, and moves them back when needed. Running out of VRAM = stuttering games.
  • Resizable BAR lets the CPU see all of VRAM at once through PCIe instead of a 256 MB window.
  • DMA-BUF lets devices share buffers without copying: camera → GPU → display.
  • KMS (kernel mode setting) is the part of DRM that sets resolution and refresh rate and tells the display engine which framebuffer to "scan out".

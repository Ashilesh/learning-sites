Many threads and processes, one computer. When they share things, chaos is one tiny timing accident away. And when they need to talk, the kernel carries their messages.

      😱 Why races are evil

      They happen only sometimes, depending on exact timing. Your program passes every test, then fails once a week in production. The part of code that touches shared data is the critical section — only one thread may be inside at a time.

      🔒 The toolbox of locks

      🚻🔑

      Mutex

      One key for the bathroom. Take the key → go in → give the key back. Others sleep while waiting.

      pthread_mutex_lock()

      🔁⏳

      Spinlock

      Wait by spinning in a loop, staring at the door. Wasteful, but great when the wait is a few nanoseconds (inside the kernel).

      spin_lock()

      📖👀

      Read-write lock

      Many readers at once, OR one writer alone. Perfect for "read often, change rarely".

      pthread_rwlock_*

      🅿️3️⃣

      Semaphore

      A counter: "3 parking spots left". wait() takes one (or sleeps), post() returns one.

      sem_wait() / sem_post()

      🛎️

      Condition variable

      "Wake me up when the pizza is ready." Sleep until another thread signals that something changed.

      pthread_cond_wait()

      ⚛️

      Atomic operations

      Special CPU instructions that do read-add-write as one unbreakable step. No lock needed for simple counters.

      atomic_fetch_add()

      🐧 Linux's trick: the futex

      Most of the time a lock is free. So glibc's mutex first tries an atomic instruction in user space — no system call at all! Only if the lock is busy does it call futex() to ask the kernel to put the thread to sleep. Fast path in user space, slow path in the kernel. 🏎️

      🍝 Deadlock: the dining philosophers

      🧸 The spaghetti puzzle

      Five friends sit at a round table with one fork between each pair. To eat spaghetti you need two forks. If everyone grabs their left fork at the same moment… everybody waits forever for the right one. Nobody eats. That's a deadlock. 😩

      Pick a strategy.

      🧩 The 4 ingredients of a deadlock (remove any one!)

      Ingredient (Coffman condition)MeaningHow to break it
      1. Mutual exclusionA fork can be held by only one personMake things shareable (rarely possible)
      2. Hold and waitHold one fork while waiting for anotherGrab everything at once, or nothing
      3. No preemptionNobody can snatch a fork from youGive up and retry (try-lock + back off)
      4. Circular waitA waits for B waits for C … waits for A✅ Always lock in the same global order
      🐧 lockdep

      The Linux kernel has a built-in deadlock detective called lockdep. In debug builds it records the order in which every lock is taken and screams the first time two code paths take the same locks in opposite orders — even if a deadlock never actually happened yet.

      ⚙️ Inside the kernel: locking at scale

      🏰 The Big Kernel Lock (gone!)

      When Linux first ran on multiple CPUs (1996), one giant lock protected almost everything — only one CPU could be in the kernel at a time. Over 15 years it was replaced by thousands of small, fine-grained locks, and finally removed in 2011 (kernel 2.6.39). Lesson: start simple, then split locks where it hurts.

      📰 RCU: Read-Copy-Update

      Readers never wait. To change data, a writer makes a copy, edits it, and swaps one pointer. Old readers keep using the old version; it's freed only after all of them are done (a "grace period"). Used all over Linux for routing tables, file lookups and more.

      // kernel-style locking (C)
spin_lock(&dev->lock);          // short, can't sleep inside
dev->count++;
spin_unlock(&dev->lock);

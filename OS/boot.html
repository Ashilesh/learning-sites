Waking Up: Booting ⏰

When you press the power button, the computer knows nothing. RAM is empty. How does it end up running Linux a few seconds later? It pulls itself up by its own bootstraps — that's why it's called booting.

🧸 In one sentence: booting is like your morning: the alarm rings (power), you open your eyes (firmware), remember who you are (boot loader), get dressed (kernel) and start your day's jobs (systemd).

🔗 The boot chain, step by step

Each step is a small program whose only job is to load the next, bigger one. Press ▶ Play.

🧾 Firmware: BIOS vs UEFI

    

      
👴 Legacy BIOS + MBR

        
  • From 1981 (the original IBM PC)
  • Reads the first 512 bytes of the disk — the MBR — and runs it
  • Only 446 bytes for boot code! So it loads a bigger loader in stages
  • MBR partitions: max 4 primary, max 2 TiB disks

      
😎 UEFI + GPT (today)

        
  • Understands file systems (FAT32) — reads a real file: EFI/ubuntu/grubx64.efi
  • Lives on the EFI System Partition, mounted at /boot/efi
  • Secure Boot: only runs signed boot loaders (via shim)
  • GPT partitions: 128 partitions, enormous disks

🥾 GRUB and the kernel

    

      

        
GRUB (GRand Unified Bootloader) shows the boot menu, then loads two files from /boot into RAM and jumps into the kernel, passing it a command line of settings.

        
$ ls /boot
config-6.8.0-45-generic   initrd.img-6.8.0-45-generic
grub/                     vmlinuz-6.8.0-45-generic
efi/                      System.map-6.8.0-45-generic
$ cat /proc/cmdline
BOOT_IMAGE=/vmlinuz-6.8.0-45-generic root=UUID=3f2a… ro quiet splash

      

      
🧸 What's "vmlinuz"?
It's the Linux kernel itself, squished (compressed — that's the z) so it loads faster. The very first thing it does is unsquish itself into memory. 🗜️

        
Kernel's first jobs (start_kernel() in init/main.c):

        
  • set up memory & page tables
  • set up interrupts & timers
  • start the scheduler and wake all CPU cores
  • start kthreadd (PID 2, parent of kernel threads)
  • run /init from the initramfs

    

  


  

    
🎒 The initramfs: a chicken-and-egg fix

    

      
🐔🥚 The puzzle
The kernel needs the disk driver to read the disk… but the driver is stored on the disk! It's like your house key being locked inside your house.
The fix: GRUB also loads a tiny backpack 🎒 — the initramfs — straight into RAM. It has just enough tools (drivers, maybe a password prompt for encrypted disks) to open the real disk.

      

    

    
$ lsinitramfs /boot/initrd.img-$(uname -r) | head
.
init
usr/lib/modules/6.8.0-45-generic/kernel/drivers/nvme/host/nvme.ko
usr/lib/modules/6.8.0-45-generic/kernel/fs/ext4/ext4.ko
usr/bin/busybox
# the initramfs mounts the real root, then:  switch_root /root /sbin/init

  


  

    
👑 systemd: process number 1

    
The kernel starts exactly one user program: /sbin/init. On most distros that's systemd. Everything else you'll ever run is its child, grandchild, great-grandchild…

    

      

        
🐧 Units & targets

          
systemd manages units: services (ssh.service), mounts, timers, sockets… A target is a group of units = a "goal state", like multi-user.target (server, text login) or graphical.target (desktop).

          
Units declare dependencies (Wants=, Requires=, After=), so systemd can start things in parallel safely.

🌙 And at bedtime: shutdown

    

      
📣
1. Ask nicely
systemd sends SIGTERM ("please finish up") to services, in reverse dependency order.

      
⏳
2. Then insist
Anything still running after a timeout gets SIGKILL. File systems are synced and unmounted.

      
🔌
3. Lights out
The kernel tells the firmware (via ACPI) to cut the power. 💤

    

    
⚠️ Why not just pull the plug?
Some of your data is still only in RAM (the page cache — Chapter 5). Pulling the plug loses it. Journaling file systems keep the disk consistent, but recent changes can still vanish.

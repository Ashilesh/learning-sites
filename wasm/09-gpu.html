Chapter 9

Reaching the GPU

Wasm has no GPU instructions of its own. It reaches the graphics card exactly the way JavaScript does, through WebGL or WebGPU, and every call crosses into a separate, locked-down GPU process.

CPU vs GPU, in one picture

Think of it like…

A CPU is a few clever chefs who can cook anything, one complex dish at a time. A GPU is thousands of line cooks who each do one simple job, all at once: perfect for pixels, 3D scenes and AI maths.

Wasm runs on the CPU. To use the GPU's cooks, it has to send them orders.

The journey of a draw call

Follow one "draw this triangle" order from Wasm down to the hardware.

Web page: renderer process (sandboxed)
Wasm modulebuilds vertex data, textures and settings in linear memory
JavaScript glueEmscripten's WebGPU bindings, or Rust's wgpu + wasm-bindgen
WebGPU or WebGL APIchecks every call; copies buffers out of Wasm memory
✉ command buffers sent across processes (IPC)
Browser GPU process (privileged)
Browser GPU layerDawn in Chrome, wgpu in Firefox, WebKit's own in Safari, ANGLE for WebGL
Native graphics APIVulkan, Metal or Direct3D 12, depending on the operating system
GPU drivervendor code that turns API calls into hardware commands
GPU hardware runs shaders on thousands of cores; draws into the page's canvas or returns results to read back
  1. The Wasm module does the CPU-side work: game logic, physics, preparing the triangle's corner positions in its linear memory.
  2. It calls an imported function. Glue code in JavaScript turns that into a real WebGPU or WebGL call.
  3. The web API checks the call is valid and safe, and copies the data out of Wasm memory (with writeBuffer or bufferData).
  4. The commands are packed up and posted to a separate process. The web page itself never touches the graphics card.
  5. In the GPU process, the browser's GPU layer checks everything again and translates shaders for this machine.
  6. It speaks the operating system's native graphics API: Metal on Apple devices, Direct3D 12 on Windows, Vulkan on Android and Linux.
  7. The driver from the GPU's maker turns that into hardware commands.
  8. The GPU runs the shaders on thousands of cores at once, and your triangle appears on the canvas.

The two web graphics APIs

WebGL 2 modelled on OpenGL ES 3.0
  • graphics only: triangles, textures, shaders
  • works in every modern browser
  • mature, huge number of tutorials
WebGPU modelled on Vulkan, Metal and Direct3D 12
  • graphics and general compute shaders (AI, physics, image processing)
  • less overhead per call, more control
  • Chrome and Edge since 2023; Safari 26 and Firefox 141 (Windows) since 2025 (approximate)

Why no shortcut to the driver?

Safety first

GPU drivers are large, powerful and historically buggy. A web page that could talk to them directly could crash your computer or read another tab's video memory.

Keeping the driver in a separate process, behind an API that checks every call, is what makes 3D on the web safe to visit.

What this means in practice

Batch your calls

Each draw crosses Wasm → JS → IPC. Fewer, bigger calls (instancing, render bundles) matter more than raw Wasm speed.

Keep data on the GPU

Upload buffers once and reuse them. Reading results back into Wasm memory is slow and asynchronous.

Use compute shaders

In-browser AI (ONNX Runtime Web, Transformers.js, WebLLM) runs models with WebGPU compute; Wasm handles tokenizing, scheduling and CPU fallback.

Render off the main thread

OffscreenCanvas lets a Web Worker running Wasm own the canvas, so drawing never blocks the page.

Shaders aren't Wasm

GPU programs are written in WGSL (WebGPU) or GLSL (WebGL). The browser translates them for each platform.

Remember
  • Wasm → JS glue → WebGPU/WebGL → GPU process → native API → driver → GPU.
  • Only the browser's separate GPU process talks to the driver. That's the safety story.
  • Batch calls and keep data on the GPU; use WebGPU compute for heavy parallel maths.

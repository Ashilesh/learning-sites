Architecture

A Wasm app has three layers: a compiler that produces a module, the module itself (a file of typed sections), and the live instance the browser builds from it inside a sandbox.

A house with two doors

Think of it like…

A house with no windows and exactly two doors. Things come in only through the imports door (whatever JavaScript chose to hand over), and go out only through the exports door.

Everything else, the module's memory, tables and code, stays inside. That's why a buggy or even malicious module can't read your other tabs or files.

Linear memory, up close

Linear memory is just a long row of numbered boxes, each holding one byte (a number from 0 to 255). Addresses start at 0.

One 64 KiB page = 65,536 boxes. The module can ask for more pages as it grows.

Inside: fine

Reading or writing any address inside the memory is allowed and very fast.

Outside: trap!

Every access is bounds-checked. Ask for an address past the end and the instance stops with an error (a "trap") instead of reading someone else's data.

JS can peek too

JavaScript sees the same bytes as an ArrayBuffer. That's how the two pass strings and images (chapter 7).

Remember
  • Three layers: toolchain → module (typed sections) → instance (live, sandboxed).
  • The instance holds linear memory, tables, globals and compiled code, all private.
  • Imports and exports are its only doors to JavaScript and the page.

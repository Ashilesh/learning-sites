Chapter 11

What comes next

The gaps from the last chapter are being closed by standard proposals. Each one climbs five phases before it becomes part of WebAssembly.

The five-step staircase

Phase 1idea accepted for study
Phase 2spec text drafted
Phase 3browsers build and test it
Phase 4being standardized
Phase 5done: part of the standard

Phases 1–3 are run by the Community Group; phases 4–5 by the W3C Working Group.

The proposals board

Where the proposals that matter most for today's limits stand, as of November 2026.

Phase 1being studied
Component ModelModules from different languages that plug together through typed interfaces (WIT).
Shared-Everything ThreadsShare GC objects, tables and functions between threads.
Memory controlFree and protect memory pages: fixing "grows but never shrinks".
Phase 2spec drafted
JS Primitive BuiltinsFaster use of JavaScript values from Wasm.
Phase 3being built
ESM Integrationimport { add } from "./add.wasm", with no loader code.
Stack SwitchingNative coroutines and green threads: better async, Go and Kotlin coroutines.
Custom Descriptors & JS InteropWasmGC objects JS can use with methods and prototypes.
Custom Page SizesMemory smaller than 64 KiB pages, for tiny devices.
Phase 4standardizing
Compact Import SectionSmaller files for modules with many imports.
Wide ArithmeticFast 128-bit maths for cryptography and big numbers.
Phase 5standardized
JS Promise Integration (JSPI)Lets synchronous Wasm code wait on async web APIs without a rewrite.

Ideas to push further

Cheaper Web API accessWeb API bindings Wasm can call through typed references, with no hand-written glue. Custom Descriptors are a first step; direct DOM access has no active proposal today.
Components in browsersLanding on servers first (WASI 0.2 in Jan 2024, WASI 0.3 with native async in Jun 2026). In browsers, a Rust image library and a Python script could share data with no glue.
Tighter GPU integrationShare buffers between Wasm memory and WebGPU without copies; use WebGPU from Wasm in workers by default.
Better threadsShared-everything threads plus lighter isolation rules, to make multicore code as easy as on desktop.
Smaller, faster startsBetter code caching, lazy function loading and standard libraries shared between modules.
AI hardwareWebNN (W3C) to reach NPUs and GPUs for neural networks, with Wasm running the logic around them.
Easier debuggingStandard DWARF support across every browser's DevTools, not only Chrome's extension.
Remember
  • Proposals climb five phases; phase 5 means standardized.
  • JSPI is done; ESM integration and stack switching are being built; the Component Model is still early in browsers.
  • Wasm 3.0 already shipped GC, 64-bit memory, exceptions, tail calls and more.

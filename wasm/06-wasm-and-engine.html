Chapter 6

Wasm rides the JS engine

Browsers didn't build a second engine for Wasm. Each one added a Wasm front door to its existing JavaScript engine, then reused its optimizing compiler, garbage collector, sandbox and threads.

  1. Both start as downloads. JS arrives as text; Wasm arrives as bytes, and the engine starts compiling them while the rest is still downloading.
  2. JS must be parsed into a tree. Wasm is just decoded and validated in one quick pass, because every type is already written down.
  3. JS starts in the interpreter, watching types. Wasm is already running real machine code from Liftoff.
  4. Warm JS gets quick machine code from Sparkplug and Maglev. Wasm is still cruising on Liftoff code.
  5. Hot code from both paths goes to the same optimizer, TurboFan. Only the JS version can be thrown away later (deopt).
  6. Underneath, both share the engine's machine-code generator, garbage collector, sandbox and the bridges that let them call each other.

What Wasm borrows from the engine

The optimizer

V8 feeds hot Wasm into TurboFan, the same back end used for hot JS. SpiderMonkey reuses Ion; JavaScriptCore uses its B3 back end for the OMG tier.

Tiering

Liftoff compiles each function on its first call. Busy functions are recompiled by TurboFan in the background. A call already running finishes in Liftoff code.

A code cache

Loaded with compileStreaming, TurboFan code is cached once it passes a size threshold, so repeat visits start faster. Liftoff code isn't cached.

The garbage collector

WasmGC objects live on the same heap as JS objects, so JS and a Kotlin or Dart module can safely hold references to each other.

Safety checks

Bounds checks on every memory access (often free on 64-bit machines thanks to big reserved "guard" regions), stack-overflow checks and the browser's process sandbox.

Call bridges

Small wrapper functions convert JS values to Wasm numbers and back. Modern engines make these calls cheap, but not free.

Debugging

Opening DevTools moves code back down to Liftoff so breakpoints and stepping work.

Remember
  • Wasm runs inside the existing JS engine, not a separate one.
  • It skips parsing and type-guessing, starts on a fast baseline compiler, then tiers up to the shared optimizer.
  • It shares the engine's code generator, garbage collector, sandbox and call bridges.

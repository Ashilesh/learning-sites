Chapter 5

Inside a JS engine

A JavaScript engine is the program inside your browser that turns JS text into instructions your CPU can run, and keeps memory tidy while it does. Wasm lives inside this same engine, so it's worth a look.

Every browser has one

V8 Chrome, Edge, Opera, Node.js, Deno

Wasm compilers: Liftoff (fast start) and TurboFan (optimizing)

SpiderMonkey Firefox

Wasm compilers: a baseline compiler and Ion (optimizing)

JavaScriptCore Safari, Bun

Wasm tiers: IPInt interpreter, BBQ (baseline), OMG (optimizing)

From here on we use V8's names. The others have the same idea with different names.

  1. Your page sends function total(price) { return price * 2 } as plain text. To the engine it's just characters so far.
  2. The parser reads the text and builds a syntax tree: "this is a function, it multiplies price by 2".
  3. The Ignition interpreter turns the tree into compact bytecode and starts running it right away. It's slow-ish, but it starts fast and notes what types it sees: "price was a number again".
  4. The function gets called a lot, so it's warm. Sparkplug, then Maglev, quickly turn it into real machine code.
  5. Now it's hot. TurboFan makes a bet, "price is always a number", and builds very fast machine code based on that bet.
  6. One day someone calls total("9") with a string! The bet fails, so the engine deoptimizes: it throws the fast code away and falls back to Ignition, then learns again.
  7. Meanwhile, the garbage collector (V8's Orinoco) finds objects nothing points to and frees their memory, mostly in the background.
  8. All of this runs on the event loop: one task at a time (a click, a timer, a network reply). A long task freezes the page, so heavy work belongs in Web Workers.

What a syntax tree looks like

The parser turns total = price * 2 into a tree. The engine walks the tree to know what to do first: multiply, then store.

Wasm skips this step entirely. Its file is already a precise list of instructions, so there's no text to parse.

Why it matters for Wasm

Wasm called from the main thread runs inside one of these tasks. If it crunches numbers for two seconds, the page can't repaint or respond for two seconds.

That's why heavy Wasm usually runs in a Web Worker: its own thread with its own loop.

The key insight

Most of the engine's early work (parsing, interpreting, watching types, guessing) exists to discover facts JavaScript doesn't state, like what type a value is. Wasm states them up front, so the engine can skip the guessing and go straight to machine code.

Remember
  • Engine pipeline: parser → interpreter → quick JIT → optimizing JIT.
  • Optimizations are bets on types; a lost bet means deoptimization.
  • A garbage collector cleans memory; the event loop runs one task at a time.

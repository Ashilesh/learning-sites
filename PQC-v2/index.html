Ten words you need before you start

1 page · 0 read

💡 In plain words

Cryptography has a lot of jargon. These ten words come up on almost every page. Learn them once and the rest of the guide gets much easier.

Word What it means in everyday language
Encryption Scrambling a message so that only someone with the right key can unscramble it
Key A long secret number that locks and unlocks data. Whoever has the key can read the data
Public key / private key A matched pair. You can hand out the public key to anyone. The private key never leaves you. What one does, only the other can undo
Key exchange Two computers that have never met agree on a shared secret key while strangers listen in, without the strangers learning the key
Digital signature A mathematical "stamp" that proves who created a piece of data and that nobody changed it afterwards
Certificate A digital ID card: "this public key belongs to mybank.com", signed by a trusted organisation (a Certificate Authority, or CA)
Protocol An agreed set of rules for how two computers talk. TLS (the padlock in your browser), SSH and VPNs are protocols
Algorithm The specific maths recipe used to encrypt, sign or exchange keys. RSA, AES and ML-KEM are algorithms
Quantum computer A new kind of computer that is extremely good at a few particular maths problems. Unfortunately, those problems are the ones today's internet security depends on
PQC (Post-Quantum Cryptography) New algorithms that run on normal computers but that quantum computers cannot break, as far as anyone knows

Part 1 · Basics

Cryptography basics

5 pages · 0 read

1.1What cryptography actually gives you

💡 In plain words

Cryptography does four jobs: it keeps secrets secret, shows that nothing was tampered with, proves who you are talking to, and stops someone denying they signed something. PQC does not change these jobs. It only swaps out the tools that a quantum computer could break.

The four properties:

  • Confidentiality: only the intended person can read the data. Like a sealed envelope. (Delivered by encryption.)
  • Integrity: the data was not changed on the way. Like a tamper-evident seal on a medicine bottle. (Delivered by hashes, MACs and AEAD tags.)
  • Authenticity: you really are talking to who you think you are. Like checking someone's ID at the door. (Delivered by signatures and certificates.)
  • Non-repudiation: whoever signed cannot later claim they did not. Like a signature on a contract in front of a witness. (Delivered by digital signatures.)

PQC does not invent new goals. It replaces the specific algorithms behind these goals that a quantum computer could break.

1.2The toolbox

💡 In plain words

Cryptography is a toolbox with about eight kinds of tool. Some are fast and work on big amounts of data (symmetric ciphers, hashes). Others are slower and are used to set things up securely between strangers (key exchange, public-key encryption, signatures). The quantum problem sits almost entirely in the second group.

Tool What it does Examples Where you meet it daily
Symmetric cipher (AEAD) Encrypts large amounts of data quickly, using one shared secret key AES-128-GCM, AES-256-GCM, ChaCha20-Poly1305 Every HTTPS page, disk encryption, Wi-Fi
Hash function Makes a short, fixed-size "fingerprint" of any data. Change one letter and the fingerprint changes completely SHA-256, SHA-384, SHA-3 Git commits, certificates, blockchain, file checksums
MAC A fingerprint made with a secret key. Proves the data is unchanged and came from someone who knows the key HMAC-SHA256, Poly1305, GMAC JWT with HS256, API request signing
KDF (key derivation function) Turns one secret into many strong keys HKDF, PBKDF2, Argon2 TLS key setup, password storage
Key exchange Two parties create a shared secret over an open network DH, ECDH, X25519 TLS handshake, SSH, WireGuard, Signal
Public-key encryption Encrypts data so only the owner of a specific private key can read it RSA-OAEP, RSA PKCS#1 v1.5 Older TLS 1.2 setups, S/MIME email, PGP
Digital signature Proves who wrote or approved some data RSA-PSS, ECDSA, Ed25519 TLS certificates, code signing, JWT RS256/ES256, git signing
KEM (key encapsulation mechanism) A modern way of doing key exchange: one side "wraps" a fresh secret using the other side's public key ML-KEM (PQC), also RSA-KEM, DHKEM The PQC replacement for key exchange

Two rules of thumb that matter later:

  1. Symmetric crypto and hashes are fast, and are mostly fine against quantum computers as long as the keys are big enough.
  2. Asymmetric crypto (key exchange, public-key encryption, signatures: anything with a public key) is where nearly all of the quantum damage happens.

1.3The padlock analogy

💡 In plain words

Symmetric crypto is one key for one box. Asymmetric crypto is an open padlock that anyone can snap shut but only you can open. Signatures work the other way round: only you can make the stamp, and anyone can check it.

  • Symmetric: one key locks and unlocks a box. It is fast, but there is a problem: how do you get a copy of the key to your friend safely in the first place?
  • Asymmetric: Alice hands out open padlocks (her public key). Anyone can snap one shut on a box, but only Alice holds the key that opens it (her private key). This solves the problem of sharing keys.
  • Signature: the same idea in reverse. Alice uses her private key to stamp a document. Anyone can check the stamp using her public key, but nobody else can make it.

In practice, systems use both. Asymmetric crypto is used briefly to agree on a secret, then the system switches to fast symmetric crypto for the actual data. This combination is called a hybrid construction in classical crypto. (This is a different thing from "hybrid PQC", which comes later in the guide.)

1.4Real example: opening https://mybank.com

💡 In plain words

In the tenth of a second before your bank's page appears, your browser and the bank (1) find each other, (2) agree on a secret key, (3) check that the bank is really the bank, and (4) start sending encrypted data. Only steps 2 and 3 can be broken by a quantum computer.

What happens in the first ~100 milliseconds, step by step:

  1. DNS (Domain Name System) lookup. Your computer asks "what is the address of mybank.com?" and gets back an IP address. Like looking up a phone number in a directory. This step is usually not protected unless you use DNSSEC (DNS Security Extensions) or DNS over HTTPS (DoH).
  2. Connection. Your browser opens a TCP (Transmission Control Protocol) or QUIC connection to that address. Like dialling the number and the other side picking up. Nothing is secret yet.
  3. TLS (Transport Layer Security) 1.3 handshake starts. Your browser sends a "ClientHello" message. It lists the encryption options the browser supports, the key exchange methods it can use (for example X25519) and the signature types it understands. Like saying "Hello, I speak English, French and Hindi. Which do you prefer?"
  4. Key exchange. Browser and bank each create a temporary key pair and swap the public parts. From these, both sides calculate the same shared secret. Anyone listening sees the public parts but cannot work out the secret, because of a hard maths problem (see 1.5). Like two people mixing paint colours in public and ending up with the same secret colour that no onlooker can reproduce.
  5. Authentication. The bank sends its certificate (its digital ID card), plus a signature called CertificateVerify that proves it holds the private key behind that certificate. Your browser checks that the certificate was issued by an authority it trusts, that the name matches mybank.com and that it has not expired. Like checking a passport: who issued it, does the photo match, is it still valid.
  6. Key schedule. A KDF called HKDF turns the shared secret into the actual encryption keys. Like cutting one master key into several working keys for different doors.
  7. Bulk encryption. Everything from now on (the page, your password, your balance) travels encrypted with AES-GCM (Advanced Encryption Standard in Galois/Counter Mode) or ChaCha20-Poly1305.

Matching this to the toolbox: key exchange (step 4), signatures and certificates (step 5), KDF (step 6), AEAD (step 7). Steps 4 and 5 are the quantum-vulnerable parts. Step 7 is not (with AES-256 or AES-128, see Part 2).

1.5The hard problems behind today's public-key crypto

💡 In plain words

Today's public-key crypto relies on maths that is easy one way and practically impossible to reverse. Multiplying two huge numbers is instant; splitting the result back into those two numbers would take normal computers longer than the age of the universe. Quantum computers change that.

Public-key crypto works because certain maths problems are easy in one direction and, as far as we know, impossible to reverse on normal computers in any reasonable time.

Problem Easy direction Hard direction Algorithms that rely on it
Integer factorization Multiply two huge primes p and q Given n = p*q, find p and q RSA (Rivest–Shamir–Adleman)
Discrete logarithm (DLP) Compute g^x mod p Given g, p and g^x mod p, find x Diffie-Hellman, DSA, ElGamal
Elliptic curve discrete logarithm (ECDLP) Compute x*G (a step on a special curve, repeated x times) Given G and x*G, find x ECDH, X25519, ECDSA, Ed25519

Everyday comparison: mixing two paints is easy; un-mixing them back into the original two colours is very hard. All three rows above are "un-mixing" problems.

Example with tiny numbers: 61 × 53 = 3233 takes no time at all. Given only 3233, finding 61 and 53 is easy here because the number is small. But with a 2048-bit number (617 digits long), the best normal-computer methods would need far longer than the age of the universe.

Keep this table in mind. In Part 2, one quantum algorithm turns all three rows from "hard" into "easy".

Part 2 · The threat

The quantum threat

8 pages · 0 read

2.1Quantum computing in one paragraph

💡 In plain words

A quantum computer is not a faster laptop. It is a special machine that is brilliant at a handful of specific maths problems. Two of those problems happen to be the foundations of internet security.

A normal bit is either 0 or 1. A qubit (quantum bit) can be in a mix of both at once (called superposition), and several qubits can be linked so they behave as one system (called entanglement). Certain algorithms use these effects to reach answers far faster than any known normal method. Quantum computers are not faster at everything; they are faster at very specific, structured problems. Unfortunately, two of those problems underpin most of today's internet security.

2.2Shor's algorithm (1994): breaks the public-key world

💡 In plain words

Shor's algorithm is the quantum recipe that "un-mixes the paint". On a big enough quantum computer, it breaks RSA, Diffie-Hellman and elliptic-curve crypto. Making the keys bigger does not help. The only fix is to switch to different maths.

Shor's algorithm solves factoring and discrete logarithms (including the elliptic-curve version) quickly on a large enough quantum computer. ("Quickly" here means in polynomial time: the work grows gently as keys get bigger, instead of exploding.) That wipes out the whole table in 1.5:

  • RSA: broken (the private key can be worked out from the public key).
  • Finite-field DH / DSA / ElGamal: broken.
  • ECDH / X25519 / X448 / ECDSA / Ed25519 / Ed448: broken.

Importantly, bigger keys do not save you. Going from RSA-2048 to RSA-4096, or from P-256 to P-521, only adds a little extra work for the quantum computer. Like making a lock twice as big when the burglar has a master key: size is not the issue. The only real fix is to move to algorithms based on different maths.

2.3Grover's algorithm (1996): only dents symmetric crypto and hashes

💡 In plain words

Grover's algorithm lets a quantum computer guess keys faster, but only by "halving the strength". A 256-bit key behaves like a 128-bit key, which is still far beyond anyone's reach. So AES and SHA survive; just use the bigger sizes.

Grover speeds up brute-force searching (trying keys one after another). Guessing a k-bit key normally takes about 2^k tries; with Grover it takes about 2^(k/2) quantum steps. In other words, it halves the number of bits of strength.

Tool Strength today Strength against Grover Verdict
AES-128 128-bit ~64-bit in theory Considered acceptable in practice, because Grover cannot easily be split across many machines and needs very long chains of quantum steps. Many policies still prefer AES-256 for data that must stay secret a long time
AES-256 256-bit ~128-bit Safe. Recommended target
SHA-256 (finding an input that matches a given fingerprint) 256-bit ~128-bit Safe
SHA-256 (finding any two inputs with the same fingerprint) 128-bit Not meaningfully helped by Grover Safe
HMAC, HKDF, ChaCha20 (256-bit key) 256-bit ~128-bit Safe

So: do not panic about AES or SHA. Prefer AES-256 and SHA-384 (Secure Hash Algorithm, 384-bit) for long-lived or high-security systems (this is what the US National Security Agency's CNSA 2.0, Commercial National Security Algorithm Suite, requires), but you do not need new symmetric algorithms.

2.4The master vulnerability table

💡 In plain words

Anything with a public key is in trouble. Anything symmetric, or any hash, is fine if you use 256-bit sizes. This single table is the map of what needs replacing.

Algorithm / mechanism Used for Quantum status Why
RSA (any size) Signatures, sending keys, encryption Broken by Shor Factoring
DH / DHE (finite field, ffdhe) Key exchange Broken by Shor Discrete log
ECDH, ECDHE (P-256, P-384, P-521) Key exchange Broken by Shor Elliptic-curve discrete log
X25519, X448 Key exchange Broken by Shor Elliptic-curve discrete log
ECDSA (P-256, P-384, secp256k1) Signatures Broken by Shor Elliptic-curve discrete log

An easy rule to remember: if it has a public key, assume it is vulnerable. If it is symmetric or a hash, assume it is fine with 256-bit sizes.

Only the public-key half of the toolbox needs new algorithms; AES-256, SHA-2 and SHA-3 stay as they are.

2.5Harvest now, decrypt later (HNDL)

💡 In plain words

Attackers can record your encrypted traffic today and keep it in storage. When a quantum computer arrives in a few years, they can unlock it. So anything that must stay secret for years is already at risk now, even though the quantum computer does not exist yet.

A large enough quantum computer does not exist yet (as of mid-2026, no machine can run Shor at a size that matters for real crypto). So why change anything now?

  • An attacker can record encrypted traffic today (VPN, TLS, messaging, backups being copied over the network) and store it. Like photocopying locked letters and keeping them in a drawer until someone invents a way to open the lock.
  • When a quantum computer arrives, they break the key exchange recorded at the start of each session, recover the session keys and decrypt everything that followed.
  • This means data that must stay secret for a long time is already at risk today: medical records, state secrets, source code, trade secrets, genetic data, financial contracts.

The attacker needs the handshake and the ciphertext, and nothing on your side shows that a copy was made.

This is why fixing key exchange is urgent, and fixing signatures is a little less urgent:

Threat When does the attacker need a quantum computer? Urgency
Decrypt recorded traffic (HNDL) Any time in the future; the data is already captured Now
Forge a signature or pretend to be a server At the moment of the attack, so the quantum computer must already exist Soon, but later than key exchange
Forge long-lived signatures (firmware, root certificate authorities, documents, code signing) Before the key is retired, which may be many years away Soon for long-lived keys; hardware security chips need planning years ahead

Why the difference? A recorded secret can be opened later. A fake signature only helps an attacker if they can make it while it still matters, so they need the quantum computer at that moment.

2.6Mosca's inequality: do I need to start?

💡 In plain words

Add up how long your data must stay secret and how long your migration will take. If that total is longer than the time until quantum computers arrive, you are already late.

Let:

  • X = years your data must stay secret,
  • Y = years your migration will take,
  • Z = years until a quantum computer big enough to break crypto exists (a "CRQC", cryptographically relevant quantum computer).

If X + Y > Z, you are already late.

Example: a hospital keeps patient records for 30 years (X = 30). Upgrading all its devices and dealing with all its vendors takes 5 years (Y = 5). Even if the quantum computer is 20 years away (Z = 20), 35 is more than 20. Start now.

Migration finishes at year 5, the data must stay secret until year 35, and the quantum computer arrives at year 20, leaving 15 exposed years.

2.7How close is a quantum computer that can break crypto?

💡 In plain words

Nobody knows the date. Estimates of how big the machine must be keep shrinking, today's machines are still far too small, and most experts point to the 2030s. Governments are planning for the early end of that range.

Facts to hold on to:

  • Breaking RSA-2048 needs thousands of logical qubits (reliable, error-corrected qubits), and each of those is built from many physical qubits (the real, error-prone hardware). A 2025 estimate by Craig Gidney (Google) cut the requirement to under one million physical qubits and about a week of running time, down from an earlier estimate of about 20 million. These estimates keep shrinking as methods improve.
  • Today's machines have hundreds to a few thousand physical qubits with limited error correction. Progress is real, but still far from the required size.
  • Expert surveys usually put the arrival somewhere in the 2030s, with a lot of uncertainty. Governments plan for the early end of that range.

2.8Official deadlines you should know

💡 In plain words

The US, the EU and other governments have published deadlines. For most regulated organisations, the practical deadline for critical systems is around 2030, with old algorithms banned by about 2035.

Body Guidance
NIST (US standards body) Published the first three PQC standards in August 2024: FIPS 203 (ML-KEM), FIPS 204 (ML-DSA), FIPS 205 (SLH-DSA). Its transition plan, NIST IR 8547, says quantum-vulnerable algorithms (RSA, ECDSA, ECDH, DH at today's common 112-bit strength) are deprecated (discouraged) by 2030 and disallowed (banned) by 2035
NSA CNSA 2.0 (US national security systems) Prefer and start using PQ algorithms from about 2025; use them exclusively for most categories between 2030 and 2033. Requires ML-KEM-1024, ML-DSA-87, LMS/XMSS for firmware signing, AES-256 and SHA-384/512
EU coordinated roadmap (2025) Member states start the transition by the end of 2026, protect high-risk systems by 2030, and as many systems as possible by 2035
UK NCSC, Germany's BSI, France's ANSSI and others Similar milestones between 2028 and 2035. BSI and ANSSI generally require hybrid (old plus new algorithm together) rather than the new algorithm alone during the transition

Takeaway: for regulated industries (government, finance, telecom, healthcare, defence suppliers), 2030 is the practical deadline for most critical systems, and planning has to happen now.

3.1Where crypto lives in the stack

💡 In plain words

Network software is built in layers, like a stack of boxes inside boxes. Your app sits on top, and the "secure tunnel" layer (TLS, SSH, VPN) sits underneath it. Most of the crypto that quantum computers threaten lives in that tunnel layer and in the certificates it uses.

diagram
Application     gRPC, REST, GraphQL, JWT/OAuth tokens, S/MIME, git signing
                (signing / token crypto lives here)
Session/Transport   TLS 1.3 / QUIC (HTTP/3) / SSH / DTLS / WireGuard / IPsec (IKEv2)
                (key exchange + authentication + bulk encryption)
PKI             X.509 certificates, CAs, OCSP, Certificate Transparency
Network         IPsec ESP, WireGuard
Link / Wireless WPA3 (SAE), Bluetooth LE Secure Connections, 5G (SUCI, AKA)

How to read the diagram: each line is a layer. Higher layers ride on top of lower ones, the way a letter goes into an envelope, the envelope into a mailbag and the mailbag onto a truck.

In a typical backend system, most of the quantum-relevant crypto sits in TLS (including its certificates), plus SSH (Secure Shell), VPNs (Virtual Private Networks), signed artifacts (containers, packages, firmware) and tokens (JWT, JSON Web Token).

3.2TLS 1.3 step by step (the most important protocol to understand)

💡 In plain words

TLS is the technology behind the padlock in your browser. Before any real data is sent, the two sides have a short "handshake" conversation: they agree on a secret key, the server shows its ID card, and both sides confirm nothing was tampered with. Only two parts of that conversation (the key agreement and the ID card) are at risk from quantum computers.

TLS 1.3 (defined in RFC 8446; an RFC, Request for Comments, is an internet standard document) is the version you should use. TLS 1.2 is still common. TLS 1.0 and 1.1 are retired and should not be used.

diagram
Client                                           Server
  | ClientHello                                    |
  |  - supported_versions, cipher_suites           |
  |  - supported_groups (e.g. x25519, secp256r1)   |
  |  - key_share: client public value              |
  |  - signature_algorithms                        |
  |  - ALPN: h2, http/1.1                          |
  |----------------------------------------------->|
  |                              ServerHello        |
  |            key_share: server public value       |
  |<-----------------------------------------------|
  |        [handshake keys derived; all below encrypted]
  |         EncryptedExtensions, Certificate,       |
  |         CertificateVerify (signature), Finished |
  |<-----------------------------------------------|
  | Finished                                       |
  |----------------------------------------------->|
  |        [application keys derived]               |
  |<============ encrypted application data =======>|

The handshake as a conversation:

  1. Client: "Hello." "Here are the TLS versions, encryption options, key exchange methods and signature types I support, and here is my half of the key exchange already, to save time."
  2. Server: "Hello back." "I picked these options. Here is my half of the key exchange." From this point both sides can calculate the same secret, so everything after this is encrypted.
  3. Server: "Here is my ID." It sends its certificate, a signature (CertificateVerify) proving it really owns that certificate, and a "Finished" check over everything said so far.
  4. Client: "Finished." The client sends its own check. If either side's check does not match, someone tampered with the conversation and the connection is dropped.
  5. Encrypted data flows both ways.

What each piece does and whether it is quantum-vulnerable:

Handshake element Role in plain words Today's algorithms Quantum status
key_share / supported_groups Agree on a temporary shared secret X25519, secp256r1, secp384r1, X448, ffdhe2048 Vulnerable (HNDL risk). Quantum-safe hybrid options now exist
Certificate The server's ID card, signed by a CA RSA or ECDSA public key, CA signature RSA/ECDSA Vulnerable (someone could pretend to be the server)
CertificateVerify The server proves it owns the private key behind its ID rsa_pss_rsae_sha256, ecdsa_secp256r1_sha256, ed25519 Vulnerable
Finished A check that nobody altered the handshake HMAC-SHA256/384 Safe
Key schedule Turn the shared secret into working keys HKDF Safe
Record protection Encrypt the actual data AES-GCM, ChaCha20-Poly1305 Safe (prefer 256-bit keys)
Session resumption (PSK) Skip the full handshake when reconnecting Secret from an earlier handshake, optionally with a new (EC)DHE exchange Safe if the (EC)DHE part is replaced by PQ or hybrid

An important property: TLS 1.3 always uses temporary (ephemeral) keys for key exchange. This gives forward secrecy: if the server's long-term key is stolen later, old sessions still cannot be decrypted using normal computers. But a quantum computer breaks the temporary exchange itself, which is why "harvest now, decrypt later" still works against forward-secret sessions.

Red steps are exposed to harvest now, decrypt later; orange steps matter once an attacker can forge signatures live; green steps stay safe.

3.3Anatomy of a cipher suite

💡 In plain words

A "cipher suite" is a name that lists which algorithms a connection will use, a bit like a recipe card. In TLS 1.2 one name covered everything. In TLS 1.3 the name only covers the symmetric part, and key exchange is chosen separately. That separation is good news: you can make key exchange quantum-safe without touching cipher suites at all.

TLS 1.2 style (everything bundled into one name):

diagram
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
     |     |         |       |    |
     |     |         |       |    +-- hash for PRF / HKDF
     |     |         |       +------- AEAD mode
     |     |         +--------------- bulk cipher + key size
     |     +------------------------- server authentication (signature algorithm)
     +------------------------------- key exchange

Reading the name left to right: "use ECDHE to agree on keys, RSA to prove identity, AES-256 in GCM mode to encrypt, and SHA-384 for hashing."

Here both the key exchange (ECDHE) and the identity check (RSA) are quantum-vulnerable. Only AES-256-GCM and SHA-384 are safe.

TLS 1.3 style (only the symmetric part is in the name; key exchange and signatures are chosen separately):

TLS 1.3 cipher suite Meaning
TLS_AES_128_GCM_SHA256 AES-128-GCM, HKDF-SHA256 (every TLS 1.3 implementation must support this)
TLS_AES_256_GCM_SHA384 AES-256-GCM, HKDF-SHA384
TLS_CHACHA20_POLY1305_SHA256 ChaCha20-Poly1305, HKDF-SHA256 (good on devices without AES hardware, such as some phones)

The other two lists TLS 1.3 negotiates are where PQC comes in:

  • supported_groups (the key exchange methods): x25519, secp256r1, secp384r1, secp521r1, x448, ffdhe2048..8192, and the new PQ and hybrid groups (see Part 5).
  • signature_algorithms: rsa_pss_rsae_sha256/384/512, ecdsa_secp256r1_sha256, ecdsa_secp384r1_sha384, ed25519, ed448, and (in future) ml_dsa_44/65/87.

So in TLS 1.3 you can upgrade key exchange to PQC without changing cipher suites at all. This is a big reason why upgrading key exchange is much easier than upgrading certificates.

3.4HTTP/2, gRPC and HTTP/3: what is actually in there?

💡 In plain words

gRPC and HTTP/2 do not do any encryption themselves. They hand that job to TLS underneath. So making gRPC quantum-safe means upgrading the TLS library under it, and every proxy or load balancer along the way.

The key insight: gRPC and HTTP/2 do not contain their own key exchange. They rely on TLS.

diagram
gRPC (Protobuf messages, RPC semantics, streaming)
  |  runs on
HTTP/2 (multiplexed streams, HPACK headers; ALPN token h2)
  |  runs on (TLS strongly recommended; browsers require it)
TLS 1.2 or 1.3  <-- ALL the cryptography is here
  |  runs on
TCP

Analogy: gRPC is the letter, HTTP/2 is the envelope format, TLS is the armoured van, and TCP is the road. Only the armoured van does the protecting.

  • gRPC (gRPC Remote Procedure Calls): in theory it can run over anything, in practice it almost always runs over HTTP/2. Security is configured as "channel credentials" (TLS or mutual TLS) and "call credentials" (tokens such as JWT or OAuth2).
  • HTTP/2 (Hypertext Transfer Protocol version 2, RFC 9113): when used over TLS, it requires TLS 1.2 or later, bans a list of weak TLS 1.2 cipher suites, and needs the ALPN (Application-Layer Protocol Negotiation) label h2. In practice HTTP/2 servers should use TLS 1.3, or TLS 1.2 with ECDHE and AEAD.
  • HTTP/3: runs over QUIC (which uses UDP, User Datagram Protocol, instead of TCP). QUIC has TLS 1.3 built in for its handshake, so the same key exchange groups and signature algorithms apply.

So, which key exchanges can a gRPC connection use? Whatever the TLS library under gRPC supports (BoringSSL in the C-core and many language runtimes, Go's crypto/tls in grpc-go, Netty/BoringSSL or JDK TLS in grpc-java, rustls in tonic):

Key exchange group (TLS 1.3) Type Quantum status
x25519 Classical ECDH Vulnerable
secp256r1 (P-256), secp384r1, secp521r1 Classical ECDH Vulnerable
x448 Classical ECDH Vulnerable
ffdhe2048 to ffdhe8192 Classical finite-field DH Vulnerable
X25519MLKEM768 Hybrid: X25519 plus ML-KEM-768 Protected against HNDL
SecP256r1MLKEM768 Hybrid: P-256 plus ML-KEM-768 Protected against HNDL
SecP384r1MLKEM1024 Hybrid: P-384 plus ML-KEM-1024 Protected against HNDL
MLKEM512 / MLKEM768 / MLKEM1024 ML-KEM on its own (IETF standardisation still being finalised) Protected, but using PQ alone is still debated

Important caveat: both sides must support a group before it can be used. Your client library, your server library and every box in between (service-mesh sidecars like Envoy, load balancers, API gateways, proxies that inspect TLS) each open and close their own TLS connection. Upgrading your app does not upgrade the link that a proxy handles.

Real example: a microservice call

diagram
Mobile app --(gRPC/TLS 1.3)--> Cloud load balancer --(gRPC/mTLS)--> Envoy sidecar --(localhost)--> Service

There are two separate TLS connections here, and each has its own key exchange and certificate chain. Like a parcel that changes vans twice: each van needs its own lock. Internet-facing hops are the most urgent for HNDL. Internal mutual TLS (mTLS, where both sides show certificates) needs attention too, especially if traffic leaves your datacentre or crosses a cloud provider's network. Also, mTLS client certificates and your internal certificate authority rely on signatures that are quantum-vulnerable, and in many companies they last a long time.

Upgrading the app is not enough: the load balancer and the sidecar each terminate TLS separately, so each needs the hybrid group.

4.1The families of maths

💡 In plain words

"Post-quantum" algorithms are not quantum technology. They are ordinary software built on different maths puzzles that quantum computers are not known to be good at. There are five families of puzzle. Two of them (lattices and hashes) supply most of the new standards.

PQC algorithms run on ordinary computers. They are called "post-quantum" because the maths problems they rely on have no known fast quantum attack (unlike factoring and discrete logs).

Family The hard puzzle Examples Strengths Weaknesses
Lattice Learning With Errors (LWE / Module-LWE), Short Integer Solution (SIS), NTRU. Roughly: solving equations that have deliberate small errors mixed in ML-KEM, ML-DSA, FN-DSA (Falcon), FrodoKEM, NTRU Fast, fairly small keys and signatures, works for many jobs The maths is newer; easy to get implementation details wrong
Hash-based Relies only on hash functions being secure SLH-DSA (SPHINCS+), LMS, XMSS The safest, most cautious choice Big signatures; some versions need careful bookkeeping; signatures only
Code-based Decoding messages that have random errors added (from error-correcting codes) HQC, Classic McEliece, BIKE Studied for decades (McEliece dates to 1978) Large keys or ciphertexts; only for key exchange
Multivariate Solving systems of many-variable equations UOV, MAYO, (Rainbow, broken in 2022) Tiny signatures Several schemes have been broken; large public keys
Isogeny Finding special maps between elliptic curves SQIsign (signatures); SIKE (KEM, broken in 2022) Very small keys SIKE was broken by a normal laptop in about an hour: a reminder that new maths can fail suddenly

The SIKE story is the best argument for two habits you will see throughout this guide: hybrid deployment (use old and new together, so one failing is not fatal) and crypto-agility (build systems so you can swap algorithms easily).

4.2How NIST got here

💡 In plain words

The US standards body NIST (National Institute of Standards and Technology) ran an open, worldwide competition from 2016. In 2024 it published the winners as official standards. A few more (HQC, FN-DSA) are still being finished. The new standards have new names, which the table below translates.

4.3ML-KEM (FIPS 203): the key exchange replacement

💡 In plain words

ML-KEM is the new, quantum-safe way for two computers to agree on a secret key. Instead of both sides mixing paint, one side sends an open box (its public key), the other puts a random secret in it, locks it and sends it back. Its messages are about 35 times bigger than today's X25519, but it is just as fast.

KEM vs Diffie-Hellman

Diffie-Hellman (DH) is symmetrical: both sides send a public value and both calculate the same secret. A KEM (Key Encapsulation Mechanism) is one-sided and has three steps:

diagram
KeyGen()           -> (public key pk, secret key sk)
Encaps(pk)         -> (ciphertext ct, shared secret ss)    // run by the sender
Decaps(sk, ct)     -> shared secret ss                      // run by the key owner

In everyday terms:

  1. KeyGen: Alice makes a padlock (public key) and its key (secret key).
  2. Encaps: Bob picks a random secret, locks it in a box with Alice's padlock and sends the locked box (the ciphertext). He keeps a copy of the secret.
  3. Decaps: Alice opens the box with her key. Now both have the same secret.
diagram
Classical ECDH (TLS today)               ML-KEM in TLS
Client: send g^a                         Client: KeyGen -> send pk (1184 B)
Server: send g^b, compute g^ab           Server: Encaps(pk) -> send ct (1088 B), keep ss
Client: compute g^ab                     Client: Decaps(sk, ct) -> ss

In TLS, the client now makes the padlock and the server does the locking. The resulting 32-byte shared secret ss goes into the same HKDF key schedule as before, so nothing else in TLS changes.

In TLS the client sends the ML-KEM public key and the server returns the ciphertext; an attacker must break both exchanges to learn the session key.

The maths idea: Learning With Errors (LWE)

💡 In plain words

Solving a few simple equations is easy. Add a tiny bit of random "noise" to each one, use hundreds of unknowns, and it becomes practically impossible, even for a quantum computer. That noisy-equations puzzle is what ML-KEM is built on.

Solving ordinary equations is easy. Suppose the secret is s = (s1, s2) and the public equations are:

diagram
3*s1 + 2*s2 = 12      -> Gaussian elimination solves this instantly
1*s1 + 4*s2 = 14      -> s1 = 2, s2 = 3

Now add a small random error to each equation, so you only see approximate answers:

diagram
3*s1 + 2*s2 = 12 + 1 (noise)
1*s1 + 4*s2 = 14 - 1 (noise)

With two unknowns you could still guess. With hundreds of unknowns, wrap-around ("modulo") arithmetic, and noise, finding s is believed to be hard even for quantum computers. That is LWE. Analogy: finding someone's exact location from a few slightly wrong GPS readings is easy in 2D, but hopeless in a space with hundreds of dimensions.

ML-KEM uses a structured version called Module-LWE. It works with polynomials in the ring Z_q[x]/(x^256 + 1) with q = 3329. This structure keeps keys small and makes the maths fast (using the Number Theoretic Transform, a cousin of the FFT).

  • Public key: a matrix A and a noisy product t = A*s + e (the secret s hidden behind the noise e).
  • Encapsulation: pick a random small r, send roughly A^T*r plus noise, plus a masked version of the message.
  • Decapsulation: use the secret s to cancel out the big terms, leaving the message plus a little noise that rounds away.

Sizes

Parameter set NIST category Public key Ciphertext Shared secret Typical use
ML-KEM-512 1 (about as strong as AES-128) 800 B 768 B 32 B Constrained cases
ML-KEM-768 3 (about AES-192) 1184 B 1088 B 32 B Default for TLS, SSH, most apps
ML-KEM-1024 5 (about AES-256) 1568 B 1568 B 32 B CNSA 2.0, high security

For comparison, an X25519 public value is 32 bytes. ML-KEM is about 35 times bigger, but very fast: often as fast as X25519 or faster.

Security properties

  • Safe even against attackers who send fake messages (the technical term is IND-CCA2). This is achieved with a technique called the Fujisaki-Okamoto transform. When unlocking, the receiver re-does the locking to check the box was made honestly. If it was not, it quietly returns a random-looking value instead of an error message (called implicit rejection). That way an attacker learns nothing from sending fake boxes.
  • Implementations must take the same time no matter what the secret is ("constant-time"). Otherwise an attacker could learn secrets by timing them. A 2023 flaw called KyberSlash (a division step whose speed depended on the secret, in some implementations) showed this is a real risk. Use well-maintained libraries, never home-made code.

4.4ML-DSA (FIPS 204): the signature replacement

💡 In plain words

ML-DSA is the new, general-purpose digital signature, the quantum-safe successor to RSA and ECDSA signatures. It is fast to check, but its signatures are about 40 to 70 times bigger than ECDSA's.

ML-DSA (Module-Lattice-Based Digital Signature Algorithm) is designed to directly replace ECDSA and RSA signatures. It is a lattice scheme based on a method called "Fiat-Shamir with Aborts": the signer creates a candidate signature, checks whether it would leak any hint about the secret key, and if so throws it away and tries again. So signing time varies a little; checking a signature is always fast.

Parameter set NIST category Public key Signature For comparison
ML-DSA-44 2 1312 B 2420 B ECDSA P-256: public key 64 B, signature 64 B
ML-DSA-65 3 1952 B 3309 B Common default
ML-DSA-87 5 2592 B 4627 B Required by CNSA 2.0

Signing can be deterministic (same input always gives the same signature) or hedged (fresh randomness mixed in, which is preferred because it resists attacks that inject hardware faults). FIPS 204 also defines a "pre-hash" version (HashML-DSA, which signs a fingerprint of a large file rather than the whole file) and a "context string" (a label so one key's signatures for one purpose cannot be reused for another).

4.5SLH-DSA (FIPS 205): the cautious signature

💡 In plain words

SLH-DSA is built only from hash functions, which we trust very much. If the newer lattice maths ever fails, SLH-DSA still stands. The price: signatures are large (8 to 50 KB) and signing is slow, so it suits things you sign rarely but must trust for decades.

SLH-DSA (Stateless Hash-Based Digital Signature Algorithm, formerly SPHINCS+) builds signatures entirely from hash functions, using a big tree of one-time and few-time signatures. If SHA-2 or SHAKE is secure, SLH-DSA is secure. That makes it the safe choice in case someone finds a flaw in lattice maths. The cost is size and speed.

Variant Public key Signature Comment
SLH-DSA-128s ("small") 32 B 7,856 B Smaller signatures, slow signing
SLH-DSA-128f ("fast") 32 B 17,088 B Faster signing, bigger signature
SLH-DSA-192s / 192f 48 B 16,224 B / 35,664 B
SLH-DSA-256s / 256f 64 B 29,792 B / 49,856 B

Good fit: things signed rarely and trusted for a long time (root keys, firmware, document archives). Poor fit: TLS handshakes or anything that signs a lot.

4.6FN-DSA (Falcon, FIPS 206 in progress)

💡 In plain words

Falcon has the smallest signatures of the lattice family, which is great when every byte counts. But it is tricky to implement safely, so leave it to specialists.

Falcon has the smallest combined public key and signature of the lattice schemes: about 897 B public key and about 666 B signature at level 1 (Falcon-512), and 1793 B / 1280 B at level 5 (Falcon-1024). That makes it attractive where bandwidth matters, such as certificate chains.

The downside: it relies on floating-point maths with random sampling, which is hard to make constant-time (see 4.3). Done carelessly, it can leak secrets through timing or power use. It is best left to specialist software and hardware.

4.7Stateful hash signatures: LMS and XMSS

💡 In plain words

LMS and XMSS are small, fast and very trustworthy hash-based signatures, and they are required today for signing firmware. The catch: each signing key is really a book of single-use pages. Use the same page twice and security collapses. So they must live in hardware that never loses track of which page is next.

LMS stands for Leighton–Micali Signature and XMSS for eXtended Merkle Signature Scheme. They are defined in RFC 8554 (LMS/HSS, Hierarchical Signature System), RFC 8391 (XMSS) and NIST SP 800-208. They are mature, small and fast, and CNSA 2.0 requires them for firmware and software signing.

The catch: each private key contains a counter that tracks which one-time key comes next. Signing twice with the same one-time key breaks security. Restoring an HSM (Hardware Security Module, a tamper-proof key safe) from backup, cloning a virtual machine, or a crash that rolls back the counter can all silently reuse a one-time key.

diagram
Good: sign(msg1) uses OTS key #41, state -> 42, state persisted BEFORE signature is released
Bad:  restore a backup that says state=41; sign(msg2) uses OTS key #41 again -> forgery becomes possible

Analogy: a chequebook where each cheque number may be used only once. If you restore an old copy of the chequebook and reuse cheque #41, a forger can now fake your signature.

Use them only inside HSMs designed to manage this counter, and only for low-volume signing such as firmware releases.

4.8Other key exchanges you will hear about

💡 In plain words

A few other quantum-safe key exchange algorithms exist as backups, mostly using code-based maths. They are useful insurance if lattices are ever weakened, and some European agencies prefer them, but they tend to be bigger.

The new algorithms are not slower, they are bigger. Key exchange messages grow by about 1 KB in each direction. Each signature grows to between 2.4 and 4.6 KB, and a single web connection carries several signatures. Most of the practical headaches in PQC come from these sizes.

4.10What can go wrong

💡 In plain words

Four things can go wrong: the maths might turn out weaker than hoped, the code might leak secrets, people might use it incorrectly, or the bigger messages might break older network equipment.

  • New attacks on the maths: lattice problems have been studied for decades, but not as long as factoring. This is exactly why governments prefer hybrid for now.
  • Implementation attacks: leaking secrets through timing, power use or deliberately induced hardware faults. Use FIPS-validated or heavily reviewed libraries (OpenSSL 3.5+, BoringSSL, AWS-LC, liboqs for prototypes, Bouncy Castle, Go standard library).
  • Misuse: reusing stateful keys, confusing draft-era Kyber with final ML-KEM, using SLH-DSA where size matters.
  • Protocol surprises: bigger handshakes break buggy network boxes, and protocols that use UDP (QUIC, DTLS, DNS, IKEv2) run into problems when messages must be split into pieces.

5.1Hybrid key exchange: belt and braces

💡 In plain words

"Hybrid" means doing the old key exchange and the new one at the same time and combining the results. An attacker then has to break both. If the new maths turns out to have a flaw, the old one still protects you today. If quantum computers arrive, the new one protects you. This is the approach the internet uses right now.

A hybrid key exchange runs a classical exchange and a PQC KEM side by side and mixes both secrets together. An attacker must break both to learn the session key. Like locking a door with two different locks from two different manufacturers.

diagram
ss_final = KDF( ss_mlkem || ss_x25519 || transcript )

Reading the formula: the final secret is made by feeding the ML-KEM secret, the X25519 secret and a record of the handshake into a key derivation function.

Why hybrid:

  1. Protects against an undiscovered flaw in ML-KEM (the SIKE lesson).
  2. Protects against bugs in newer, less-tested code.
  3. Satisfies regulators who still require classical algorithms during the transition, while still stopping "harvest now, decrypt later".

The TLS 1.3 hybrid groups officially registered with IANA (Internet Assigned Numbers Authority, the internet's numbering registry):

Named group Code number What is inside Size of the client's message
X25519MLKEM768 0x11EC X25519 + ML-KEM-768 1184 + 32 = 1216 B
SecP256r1MLKEM768 0x11EB P-256 + ML-KEM-768 1184 + 65 = 1249 B
SecP384r1MLKEM1024 0x11ED P-384 + ML-KEM-1024 1568 + 97 = 1665 B
X25519Kyber768Draft00 0x6399 Pre-standard Kyber Obsolete; move away from it

X25519MLKEM768 is the de facto internet default. SecP384r1MLKEM1024 is the one that fits CNSA 2.0 and FIPS-focused environments.

There is also X-Wing, a ready-made combination of X25519 and ML-KEM-768 designed for use inside applications (HPKE and custom protocols), and the general HPKE framework (Hybrid Public Key Encryption, RFC 9180), which is being extended to support ML-KEM.

5.2What a hybrid TLS 1.3 handshake looks like

💡 In plain words

The handshake is the same conversation as before. The only differences are that the first two messages carry a bigger key exchange (about 1.2 KB each way) and that certificates are still the old kind. That is why this upgrade has spread so fast: it needs no changes to certificates or apps.

diagram
Client                                                      Server
 ClientHello (now about 1.4 to 1.6 KB, was about 0.5 KB)
   supported_groups: X25519MLKEM768, x25519, secp256r1
   key_share: X25519MLKEM768 = [ML-KEM pk 1184 B || X25519 pk 32 B]
 --------------------------------------------------------->
                                                      ServerHello
   key_share: [ML-KEM ct 1088 B || X25519 pk 32 B]
 <---------------------------------------------------------
  both sides: ss = ss_mlkem || ss_x25519, then the normal HKDF schedule
  Certificate (still classical RSA/ECDSA today), CertificateVerify, Finished

Notes:

  • The client guesses which group the server will choose and sends its key share for that group straight away. If it guesses wrong, the server replies "please try again with this one" (a HelloRetryRequest), which costs an extra round trip. To avoid that, browsers send both a hybrid share and a plain X25519 share in the first message, at the cost of a bigger ClientHello.
  • This upgrade changes only the key exchange. Certificates, the TLS cipher suite and the application stay the same. That is why it has spread so widely: it fixes HNDL without waiting for the certificate system to change.

Real-world gotcha: the oversized ClientHello

💡 In plain words

The first message is now too big to fit in one network packet. Some old firewalls and load balancers cannot cope with that and drop the connection. If something breaks only when PQ is switched on, blame the network box in the middle first.

The ClientHello now often goes over the size of one TCP packet or one QUIC Initial packet. Early rollouts ran into buggy network boxes, firewalls and old servers that failed when the ClientHello was large or split across packets. Most have been fixed, but internal appliances, deep-packet-inspection firewalls, old load balancers and outdated servers are still the usual suspects. If a service times out only when PQ is enabled, suspect a box in the middle of the network first.

5.3The harder half: PQ authentication and certificates

💡 In plain words

Swapping the ID-card part (certificates) to PQC is much harder than swapping key exchange. A web connection carries four or more signatures, and PQ signatures are big, so the handshake would grow from about 3 KB to about 15 KB. That slows connections down, and changing certificates also needs agreement from browsers and certificate authorities worldwide. Several clever ideas are being tested to shrink the problem.

A typical TLS server sends: its own (leaf) certificate (a public key plus a CA signature), an intermediate certificate (a public key plus a root signature), a CertificateVerify signature, and often Certificate Transparency signatures (SCTs, proof that the certificate was publicly logged).

Chain made of Approx. bytes spent on identity
ECDSA P-256 about 2 to 4 KB in total, including certificate overhead
RSA-2048 about 3 to 5 KB
ML-DSA-65 everywhere about 14 to 17 KB (2 public keys at 1952 B plus 3 signatures at 3309 B is already about 13.8 KB, before SCTs and overhead)

What that means: TCP normally sends only about 10 packets (about 14 KB) before waiting for a reply from the other side. So a PQ chain can cost an extra round trip, which users feel as delay. QUIC has a similar rule: a server may send only three times as much data as it has received before the client proves its address (the "anti-amplification limit"). This is why browsers and CAs have not yet issued PQ certificates for the public web, and why work focuses on shrinking the problem:

Idea What it does, in plain words
Merkle Tree Certificates (MTC) Instead of a signature on every certificate, the CA publishes a big list and the client checks a short proof that your certificate is on it. One PQ signature then covers many certificates. Chrome and Cloudflare began experiments in 2025
Certificate compression (RFC 8879) and leaving out intermediates the client already has Sends fewer bytes, though PQ keys and signatures do not compress well
KEMTLS / KEM-based authentication The server proves its identity by unlocking a KEM box, instead of signing
FN-DSA for leaf and intermediate certificates Smaller signatures, with the implementation warnings from 4.6
Composite / hybrid signatures One certificate holds both an old (for example ECDSA) and a new (ML-DSA) key and signature, and is valid only if both check out
Dual-chain or alternative-signature extensions Old clients use the old chain; PQ-aware clients use the new one

Private certificate systems (service-mesh CAs, internal mTLS, device identity, code signing) do not need browsers to agree, so they are the natural place to start using ML-DSA.

6.1Guiding principles

💡 In plain words

Five rules: find all your crypto first; fix key exchange before signatures; build so the next change is easy; use old and new together during the transition; and do the most important things first, not the easiest.

  1. You cannot fix what you cannot see. Make an inventory first.
  2. Fix key exchange first (because of harvest now, decrypt later), then identity and signatures.
  3. Be crypto-agile: make the next algorithm swap cheap, because this will not be the last one.
  4. Use hybrid by default during the transition, unless a regulation says otherwise.
  5. Prioritise by how long data must stay secret and how exposed it is, not by what is easiest.

6.2The phases

💡 In plain words

The migration runs in eight phases: get someone in charge, find all your crypto, rank it by risk, grab quick wins on internet-facing systems, move on to internal links, then tackle certificates and signatures, then the long tail of devices and vendors, and finally keep checking that it all stays fixed.

💡 In plain words

6.5Designing for crypto-agility

💡 In plain words

"Crypto-agility" means you can change an algorithm by changing a setting, not by rewriting your software. The main tricks: let libraries choose algorithms, label every key and signature with its algorithm, leave room for much bigger keys and signatures, and keep crypto behind one small internal interface.

Crypto-agility means you can replace an algorithm with a configuration change and a rollout, not a rewrite.

Do Do not
Use library defaults and let the protocol choose (let TLS pick groups) Fix a single curve, for example CurvePreferences set to X25519 only, which silently blocks PQ upgrades
Store an algorithm label next to every signature, key and ciphertext Assume signatures and keys have a fixed length in your database or message format
Make database columns, message fields, headers, QR codes and log lines big enough for keys and signatures of several KB Put signatures in places with hard limits, such as 4 KB cookies or 8 KB HTTP header limits, without checking
Keep crypto behind a small internal interface (sign, verify, encapsulate) with swappable back-ends Scatter direct calls to RSA or ECDSA all over the codebase
Make certificate and key rotation automatic and routine Rely on manual certificate renewals every few years
Put version numbers on your protocols and message formats Hard-code protocol assumptions into firmware that cannot be updated
Test with large handshakes in CI (QUIC, UDP paths, links with small packet sizes) Test only the happy path on a fast office network

Example: a JWT signed with ML-DSA-65 carries a 3309-byte signature, which becomes about 4.4 KB once base64url-encoded (turned into text). A login token that fits comfortably in an Authorization header today as ES256 (64-byte signature) may now go over proxy header limits, break cookies, or slow down every internal hop. Options: use reference tokens (a short ID that the server looks up), keep tokens short-lived and check ML-DSA signatures only at the edge, or use symmetric MACs between trusted internal services.

6.6Symmetric and hash upgrades (low drama)

💡 In plain words

For symmetric crypto and hashes, just use the bigger versions (AES-256, SHA-384) for new work, and get rid of algorithms that were already broken long before quantum (3DES, RC4, MD5, SHA-1). A strong pre-shared secret can give you quantum protection right away while you wait for full PQC support.

  • For new designs, prefer AES-256-GCM and ChaCha20-Poly1305, SHA-384/512, HMAC-SHA-384 and HKDF-SHA-384.
  • Avoid 3DES, RC4, CBC mode with padding, MD5 and SHA-1 (these were already broken by normal computers).
  • Passwords: use Argon2id, scrypt or PBKDF2 with strong settings. Quantum is not the weak point here; weak passwords are.
  • For existing protocols that use fixed keys, adding a 256-bit pre-shared key (IPsec PSK, WireGuard PSK, TLS 1.3 PSK with (EC)DHE) gives a quick quantum-resistant layer while you wait for PQ key exchange, as long as the key is shared securely and changed regularly.

6.7Common pitfalls (learn from early adopters)

💡 In plain words

The ten mistakes early adopters made, in short: old network boxes that choke on big messages, hard-coded algorithm lists, forgetting the hops behind the edge, apps that pin certificates, size limits everywhere, small devices that cannot cope, using draft code, waiting on FIPS validation, mishandling single-use signature keys, and declaring victory too early.

  1. Network boxes that fail on a ClientHello over 1.5 KB or on QUIC first packets split into pieces.
  2. Hard-coded algorithm lists in config, Helm values, mesh policies or code that leave out PQ groups.
  3. TLS ending at several places: you upgraded the edge, but the CDN-to-origin link and the sidecar hops are still classical.
  4. Certificate pinning in mobile apps (the app only accepts one specific certificate or key): it will break when you change keys or CAs.
  5. Size assumptions in database columns, protocol fields, DNS packets, QR codes, smart cards and small devices.
  6. Embedded devices with too little storage, memory or CPU to check PQ signatures: check ML-DSA and LMS requirements early.
  7. Draft versus final: do not ship Kyber-draft or Dilithium-draft code; use implementations that follow FIPS 203/204/205.
  8. FIPS validation lag: certified modules with ML-KEM and ML-DSA are only now appearing; check what your compliance rules require.
  9. Mishandling stateful hash signatures (LMS/XMSS counter reuse).
  10. Declaring victory after the edge upgrade: certificates, tokens, code signing and internal links are still classical.

💡 In plain words

These exercises let you see PQC working on your own machine: check what your tools support, test whether a real website uses quantum-safe key exchange, create PQ keys and certificates, and compare their sizes with the old kind. Every command comes with a line explaining what it does.

7.1See which algorithms your OpenSSL supports

What this does: lists the quantum-safe algorithms your copy of OpenSSL knows about. If ML-KEM and ML-DSA show up, you are ready for the rest of the labs.

bash
openssl list -kem-algorithms

7.2Test a live server's key exchange

What this does: connects to a real website and asks it to use the hybrid quantum-safe key exchange. If the site supports it, OpenSSL reports that it was used. The second command does the same with the old method, for comparison.

bash
# Force the hybrid group and see if it is negotiated
openssl s_client -connect cloudflare.com:443 -tls1_3 -groups X25519MLKEM768 </dev/null 2>&1 | grep -i -E 'group|Cipher|Protocol'

# Compare with classical only
openssl s_client -connect cloudflare.com:443 -tls1_3 -groups X25519 </dev/null 2>&1 | grep -i group

# curl (needs a build against OpenSSL 3.5+ or BoringSSL)
curl -v --curves X25519MLKEM768 https://cloudflare.com 2>&1 | grep -i -E 'SSL connection|group'

Look for a line such as Negotiated TLS1.3 group: X25519MLKEM768. If the service does not support the group, you will see the handshake fail (if you offered only that group) or fall back to another group (if you offered several).

7.3Generate and use an ML-KEM key pair

What this does: walks through the "padlock and box" from 4.3 by hand. You make a padlock (key pair), lock a random secret in a box (encapsulate), unlock it (decapsulate), and confirm both sides ended up with the same secret.

bash
openssl genpkey -algorithm ML-KEM-768 -out mlkem.key
openssl pkey -in mlkem.key -pubout -out mlkem.pub

# Sender: encapsulate to the public key -> ciphertext + shared secret
openssl pkeyutl -encap -inkey mlkem.pub -pubin -out ct.bin -secret ss_sender.bin

# Receiver: decapsulate with the private key
openssl pkeyutl -decap -inkey mlkem.key -in ct.bin -secret ss_receiver.bin

cmp ss_sender.bin ss_receiver.bin && echo shared secrets match
ls -l ct.bin mlkem.pub   # ct is 1088 bytes, public key DER is slightly over 1184

7.4Sign and verify with ML-DSA, and make a PQ certificate

What this does: creates a quantum-safe signing key, signs a small file and checks the signature. Then it makes a test certificate with that key, so you can see how much bigger PQ certificates are.

bash
openssl genpkey -algorithm ML-DSA-65 -out mldsa.key
openssl pkey -in mldsa.key -pubout -out mldsa.pub

echo 'release v1.2.3' > msg.txt
openssl pkeyutl -sign -inkey mldsa.key -rawin -in msg.txt -out msg.sig
openssl pkeyutl -verify -pubin -inkey mldsa.pub -rawin -in msg.txt -sigfile msg.sig
ls -l msg.sig            # 3309 bytes

# Self-signed PQ certificate
openssl req -x509 -new -key mldsa.key -subj '/CN=pqc-test.local' -days 30 -out mldsa.crt
openssl x509 -in mldsa.crt -noout -text | head -20
wc -c mldsa.crt          # note the size compared with an ECDSA certificate

Exercise: make an ECDSA P-256 certificate the same way and compare the file sizes. This makes the size problem from Part 5 easy to see.

7.5A fully post-quantum local TLS 1.3 connection

What this does: runs a tiny web server on your own machine that uses both a PQ certificate and hybrid key exchange, then connects to it. This is what a fully quantum-safe connection looks like.

bash
# Terminal 1: server with ML-DSA cert and hybrid group
openssl s_server -accept 4433 -cert mldsa.crt -key mldsa.key -tls1_3 -groups X25519MLKEM768 -www

# Terminal 2: client
openssl s_client -connect localhost:4433 -tls1_3 -groups X25519MLKEM768 -CAfile mldsa.crt </dev/null 2>&1 | grep -i -E 'group|signature|Verification'

Record the handshake with Wireshark or tcpdump on the loopback interface, and compare the sizes of the ServerHello and Certificate messages with a run using classical algorithms.

7.6Go: ML-KEM in the standard library, and PQ in gRPC

What this does: the same padlock-and-box exercise as 7.3, written in Go. It prints true if both sides got the same secret, followed by the public key and ciphertext sizes.

go
package main

import (
    "bytes"
    "crypto/mlkem"
    "fmt"
)

func main() {
    dk, err := mlkem.GenerateKey768()   // receiver generates keypair
    if err != nil { panic(err) }
    ek := dk.EncapsulationKey()          // public key (1184 bytes)

    ss1, ct := ek.Encapsulate()          // sender: shared secret + ciphertext (1088 bytes)
    ss2, err := dk.Decapsulate(ct)       // receiver recovers the secret
    if err != nil { panic(err) }

    fmt.Println(bytes.Equal(ss1, ss2), len(ek.Bytes()), len(ct))
}

For gRPC in Go, you normally write no KEM code at all. With the standard credentials and Go 1.24 or later, hybrid key exchange happens automatically:

go
creds := credentials.NewTLS(&tls.Config{ MinVersion: tls.VersionTLS13 })
conn, err := grpc.NewClient("api.example.com:443", grpc.WithTransportCredentials(creds))

Things to know:

  • Setting CurvePreferences yourself replaces the defaults. If you list only classical curves, you switch PQ off.
  • The setting GODEBUG=tlsmlkem=0 turns the hybrid default off. That is useful for debugging network-box problems, not for production.
  • In recent Go versions, the TLS connection details show which key exchange was used (look for ConnectionState.CurveID in Go 1.25 and later). You can log it from a gRPC interceptor or via the peer's AuthInfo to build a dashboard of PQ adoption.

8.3Myths

💡 In plain words

Common misunderstandings, and the truth behind each one.

Myth Reality
Quantum computers will break all encryption They break public-key crypto (RSA, DH, ECC). AES-256 and SHA-2/3 stay safe
We have time, quantum computers do not exist yet Recorded traffic is at risk now (HNDL), and migrations take years
Bigger RSA or ECC keys fix it They do not; Shor's algorithm copes easily with bigger keys
Quantum key distribution (QKD) is the answer QKD needs special hardware and dedicated links, and does not solve identity checking; agencies such as NSA, NCSC, ANSSI and BSI recommend PQC instead for general use
PQC algorithms are experimental ML-KEM, ML-DSA and SLH-DSA are official NIST standards and run at internet scale. The caution is about how mature implementations are and long-term analysis of the maths, which is why hybrid is used
PQC is too slow ML-KEM is about as fast as X25519; the cost is mostly extra bytes, not CPU
TLS forward secrecy protects us It protects against the server's key being stolen later, not against a quantum computer breaking the temporary key exchange

  4. Shor's algorithm solves factoring and discrete logs efficiently, so a bigger key barely helps. Grover only halves the strength of symmetric keys, so a 256-bit key still has about 128-bit strength against a quantum computer.
  5. In DH, both sides send public values. In a KEM, one side sends a public key and the other sends back a ciphertext (the locked box). In TLS, the client sends the ML-KEM public key (1184 B plus 32 B for X25519) and the server returns the ciphertext (1088 B plus 32 B).
  6. Hybrid protects against an unknown weakness or bug in ML-KEM. The cost is about 1.2 KB extra in each direction compared with X25519 alone.
  7. Signatures are 2.4 to 4.6 KB each and a chain carries several, adding 10+ KB to the handshake. Certificates also involve CAs, browsers, root programs and long-lived trust anchors that all have to agree. Key exchange can be upgraded by two endpoints on their own.
  8. ML-DSA: general purpose. FN-DSA: smallest size, needs expert implementation. SLH-DSA: most cautious, low volume, tolerates size. LMS/XMSS: firmware signing in HSMs with careful counter handling.
  9. Examples: network boxes failing on large ClientHellos, database or header size limits (tokens, cookies), UDP fragmentation, packet size and TCP start-up effects, small devices running out of storage, certificate pinning.
  10. The Go version (1.24 or later), any CurvePreferences or GODEBUG=tlsmlkem=0 override, and the server or proxy in between that handles TLS (its library and group list).

X.509 certificates in depth

💡 In plain words

This appendix opens up a certificate (the server's digital ID card) to show what is inside, which parts are at risk, how long different certificates last, and how quantum-safe certificates are being designed.

A.1What a certificate is

💡 In plain words

A certificate is a signed note saying "this public key belongs to this name". Every certificate involves two algorithms: the one for the owner's key and the one the authority used to sign it. Both need replacing, and the weakest one decides your risk.

A certificate (X.509 version 3, RFC 5280) is a signed statement: this public key belongs to this subject. The signer is a Certificate Authority (CA). Anyone who trusts the CA can check the statement without contacting anyone. Like a passport: you trust it because you trust the government that issued it.

Field What it holds Quantum relevance
Version, serial number v3 and a unique number per CA None
signatureAlgorithm (inside the signed part) Which algorithm the CA used to sign this certificate (for example sha256WithRSAEncryption, ecdsa-with-SHA256) Vulnerable if RSA or ECDSA/EdDSA
Issuer Name of the CA None
Validity (notBefore, notAfter) When the certificate is valid from and to Decides how long a vulnerable key stays in use
Subject Who the certificate is for (name, organisation) None
subjectPublicKeyInfo The owner's public key and its algorithm (RSA, EC, Ed25519, and in future ML-DSA or ML-KEM) Vulnerable if RSA or EC
Extensions Extra details: SAN (allowed hostnames and IPs), Key Usage, Extended Key Usage, Basic Constraints, SKI/AKI, AIA, CRL distribution points, SCTs Key Usage matters for KEM certificates (see A.5)
signatureValue (outside the signed part) The CA's signature itself Vulnerable if RSA or ECDSA/EdDSA

Key point: every certificate involves two algorithms that can be different: the algorithm of the owner's key and the algorithm of the issuer's signature. For example, an ECDSA P-256 server certificate can be signed by an RSA-4096 intermediate. Migration must cover both, and the weakest link in the chain decides your exposure.

A.2Chain of trust and lifetimes

💡 In plain words

Certificates form a chain: a root authority vouches for an intermediate, which vouches for your server. Roots last 20 to 30 years, so a root created today could still be in use when quantum computers arrive. That is why roots and intermediates are the top priority, and short-lived server certificates are the easy part.

The longer a key lives, the longer it stays exposed, which is why roots and intermediates come before leaves.

diagram

               signs -> Leaf certificate (your server)         lifetime: days to ~1 year
Level Typical lifetime Why it matters for PQC
Root CA key 20 to 30 years, often kept offline in an HSM Highest priority: a key created today may still be trusted after quantum computers arrive. Updating trust lists in devices takes years
Intermediate CA key 5 to 10 years High priority
Leaf (TLS server) Public web: getting shorter under CA/Browser Forum rules (200 days from March 2026, planned 100 days in 2027 and 47 days in 2029) Short life limits exposure and makes switching algorithms easy
mTLS and workload certificates (SPIFFE, service mesh) Hours to days Easy to replace, so ideal for PQ pilots
Code-signing, S/MIME, document-signing, device identity certificates 1 to 15+ years Long-lived signatures are at real risk

Short certificate lifetimes are a free crypto-agility win: if every certificate is automatically reissued every few weeks (with ACME or cert-manager), switching the key algorithm is just a configuration change.

A.3Validation and revocation

💡 In plain words

When your browser checks a certificate it verifies several signatures, the dates, the name and whether the certificate has been cancelled. Every one of those signatures will grow from tens of bytes to thousands with PQC.

When a client checks a chain, it verifies: the signature at every level (this is where RSA/ECDSA checking happens), the validity dates, that the hostname matches the SAN list, Basic Constraints and Key Usage, and whether the certificate has been revoked (cancelled) using CRLs, OCSP or simply short lifetimes. Certificate Transparency adds SCTs, extra signatures from public logs, and these will also need PQ replacements eventually.

Every signature in that list is a place where a PQ signature will be 2.4 to 4.6 KB instead of 64 to 256 bytes. That is the size problem described in 5.3.

A.4Where certificates live in a typical stack

💡 In plain words

A.5What a PQ certificate looks like

💡 In plain words

A quantum-safe certificate is still the same kind of certificate. Only the algorithm labels and the key and signature bytes change, and it gets about six times bigger.

A PQ certificate is still X.509. Only the algorithm identifiers (OIDs, official ID numbers for algorithms) and the key and signature bytes change.

Two details worth knowing:

  • KEM certificates: a KEM public key cannot sign anything, so an ML-KEM certificate cannot be used for CertificateVerify. It is used for encryption-style identity checks (KEMTLS, S/MIME encryption).   • Size: an ML-DSA-65 server certificate is about 5.5 to 6 KB (a 1952 B public key, plus a 3309 B CA signature, plus names and extensions), compared with about 0.5 to 1 KB for an ECDSA P-256 server certificate.

A.6Transition models for certificates

💡 In plain words

There are five ways to move certificates to PQC: go fully PQ, put both old and new keys in one certificate, attach the new key as an optional extra, run two separate chains side by side, or switch to a new log-based design. Private systems can start now; the public web is waiting for browsers to decide.

Model How it works Pros Cons
Pure PQ certificate Certificate and chain use only ML-DSA (or SLH-DSA, FN-DSA) Simplest, smallest long-term end state Old clients cannot use it; no classical safety net
Composite certificate One certificate, one key made of two keys (for example ML-DSA-65 plus ECDSA P-256), one combined signature; valid only if both check out One chain; protects against flaws in either scheme; fits the hybrid idea New algorithm IDs; clients must understand composites; size is the sum of both

Rule of thumb: private certificate systems can pilot pure PQ or composite now; the public web is waiting for browser and CA/Browser Forum decisions. A.7Inspecting certificates in practice

What these commands do: the first shows which algorithms and expiry dates a live website's certificate chain uses. The second inspects a certificate file. The third gives a rough total size of a site's chain.

openssl s_client -connect example.com:443 -showcerts </dev/null 2>/dev/null | openssl x509 -noout -text | grep -E 'Signature Algorithm|Public Key Algorithm|Public-Key|Not After'

# Inspect a certificate file

# Check a whole chain's sizes (a quick PQ size-impact estimate)
openssl s_client -connect example.com:443 -showcerts </dev/null 2>/dev/null | wc -c

Appendix B · CBOM

CycloneDX and the CBOM in depth

7 pages · 0 read

B.1What CycloneDX is, and what a CBOM adds

💡 In plain words

CycloneDX is a standard file format for listing what is inside your software. Since version 1.6 it can also list your crypto. That list (the CBOM) tells you exactly where RSA, ECDSA and friends are hiding, who owns them, and lets you automatically block new vulnerable crypto from creeping in.

CycloneDX is an open "bill of materials" standard (an Ecma International standard, ECMA-424). It is best known for SBOMs: lists of software components, versions, dependencies and vulnerabilities. From version 1.6 it added proper support for cryptography, giving us the CBOM (Cryptographic Bill of Materials): a list of crypto assets in the same machine-readable format and tools as your SBOM. Later versions extend the crypto model further, so check which version your tools produce.

Why a CBOM matters for PQC:

  • Migration starts with knowing where RSA, ECDSA, DH, X25519 and certificates are used. A CBOM is that list in a structured, searchable form.
  • It links each piece of crypto to the software that uses it (libraries, services, container images), so owners can be assigned.
  • It can be produced on every build, compared between releases and checked in CI (for example, fail the build if someone adds RSA-1024).
  • It records quantum-security information, so you can filter for vulnerable items automatically.

B.2The data model

💡 In plain words

A CBOM records four kinds of item: algorithms, certificates, protocols and key material. Items point to each other (a protocol points to the algorithms it uses). The most useful field is a "quantum security level" where 0 means "broken by quantum".

A crypto asset is a normal CycloneDX component with "type": "cryptographic-asset" and a cryptoProperties object. The assetType says which kind of item it is:

assetType Describes Key properties
algorithm A building block in use (AES-256-GCM, X25519, ML-KEM-768, ECDSA P-256, SHA-384) algorithmProperties: primitive (for example ae, signature, kem, key-agree, hash, mac, kdf), parameterSetIdentifier, curve, mode, padding, classicalSecurityLevel, nistQuantumSecurityLevel, cryptoFunctions, implementation platform and execution environment
certificate An X.509 or similar certificate certificateProperties: subjectName, issuerName, notValidBefore, notValidAfter, signatureAlgorithmRef, subjectPublicKeyRef, certificateFormat, certificateExtension
protocol TLS, SSH, IPsec, IKE, WPA and similar protocolProperties: type, version, cipherSuites (each pointing to algorithms), IKEv2 transform types, cryptoRefArray of everything the protocol uses
related-crypto-material Keys and other material (public key, private key, secret key, ciphertext, signature, nonce, salt, token, shared secret) relatedCryptoMaterialProperties: type, size, format, state (active, expired, revoked and so on), algorithmRef, creation and expiry dates

Items are linked by references (bom-ref values) and the dependencies graph. A protocol points to its cipher suites and algorithms; a certificate points to its signature algorithm and public key; a service or library can depend on the protocol, certificate and key items it uses.

The field that makes the CBOM a PQC tool is nistQuantumSecurityLevel: values 1 to 5 match NIST's PQC strength categories, and 0 means the algorithm gives no quantum security, in other words it is quantum-vulnerable (RSA, DH, ECC). Symmetric and hash algorithms get levels matching their strength.

B.4Using a CBOM to find quantum-vulnerable items

💡 In plain words

Because a CBOM is just a JSON file, ordinary tools can search it. One command lists every vulnerable algorithm; another lists every certificate with its expiry date.

Because it is plain JSON, ordinary tools work. With jq:

bash
# All algorithms with no quantum security (RSA, DH, ECC, and so on)
jq -r '.components[] | select(.type=="cryptographic-asset" and .cryptoProperties.assetType=="algorithm" and .cryptoProperties.algorithmProperties.nistQuantumSecurityLevel==0) | .name' cbom.json

# Certificates and when they expire
jq -r '.components[] | select(.cryptoProperties.assetType=="certificate") | [.name, .cryptoProperties.certificateProperties.notValidAfter] | @tsv' cbom.json

# Protocols that reference a vulnerable algorithm (join on bom-ref in your script or SIEM)

Typical reports you can build from a CBOM: number of vulnerable algorithms per application, certificates expiring after 2030 that rely on RSA or ECDSA, services that only use classical groups, and trends in PQ adoption across releases.

B.7Operating the CBOM

💡 In plain words

Treat the CBOM as a living document: regenerate it on every release, compare versions, block bad changes automatically, assign every item an owner, and track progress with a few simple numbers.

  • Generate it on every build and release, store it with the SBOM and the build, and sign it.
  • Compare versions in CI and flag any newly added vulnerable algorithm or any removed PQ group.
  • Automatic policy checks: for example, block any new RSA key under 3072 bits, any TLS below 1.3 on external listeners, and any certificate that stays valid beyond your cut-off date.
  • Assign ownership: link each item to a team, service and data classification, so the migration to-do list has owners.
  • Track progress: percentage of endpoints with hybrid key exchange, number of classical-only certificates in your most important systems, and number of long-lived RSA/ECC keys left.
  • Keep the model current: re-check the CycloneDX specification version and algorithm list when you adopt new PQ algorithms such as ML-DSA, SLH-DSA or composite types, because new entries are being added over time.

Appendix D · Keys & HSMs

Key management, data at rest, HSMs and randomness

5 pages · 0 read

💡 In plain words

Most PQC talk is about data moving over networks. But stored data and the keys that protect it matter just as much, because long-lived secrets are exactly what "harvest now, decrypt later" targets.

D.1Envelope encryption: the hidden RSA/ECC dependency

💡 In plain words

Stored data is usually locked with a data key, and that data key is itself locked with a master key. If the master key is RSA or ECC, a thief who copies both today can unlock everything later. If the master key is AES-256 and never leaves the key vault, you are safe.

Cloud KMS (Key Management Service), databases, backup tools and disk encryption almost all use envelope encryption:

diagram
Data  --encrypted with-->  DEK (data encryption key, AES-256)
DEK   --wrapped with--->   KEK (key encryption key, held in KMS / HSM)
Stored together: ciphertext + wrapped DEK

Analogy: your documents are in a locked box (encrypted with the DEK). The key to that box is sealed in an envelope (wrapped with the KEK) and taped to the box. Whether the whole thing is safe depends on how strong the envelope is.

Master key (KEK) type Quantum exposure
AES-256 symmetric KEK inside a KMS or HSM (AES-GCM or AES key wrap) Safe: only Grover applies
RSA or ECC KEK (for example RSA-OAEP wrapping, ECIES) Vulnerable: anyone who copies the data and the wrapped data key today can unwrap it once a quantum computer exists
Keys imported or exported between systems using RSA wrapping (for example "bring your own key" setups) The wrapping during transport is a short HNDL exposure for the key itself

What to do: prefer symmetric master keys that never leave the HSM or KMS; check which wrapping algorithm is used when keys are imported, exported or copied between regions; and re-wrap existing data keys that were wrapped with an asymmetric master key. When asymmetric wrapping is unavoidable (sending data to someone who only has a public key), use HPKE with a hybrid KEM or ML-KEM plus AES-256-GCM.

D.2Backups, archives and file exchange

💡 In plain words

Backups and archives encrypted to someone's RSA or ECC public key can be opened later if stolen. Re-encrypt the long-lived ones, use quantum-safe transfer, and, simplest of all, delete what you no longer need.

  • Archives encrypted to RSA or ECC recipients (PGP, S/MIME, custom scripts) can be decrypted later if the archive is stolen. Re-encrypt long-retention archives using symmetric keys or PQ recipients.
  • File transfer (SFTP, managed file transfer products, partner exchange) should use the hybrid SSH or TLS groups, and file contents should be encrypted with AES-256.
  • Keep data for less time: data you no longer hold cannot be harvested later. Deleting data you do not need is a genuine quantum defence.

D.3HSMs and KMS

💡 In plain words

HSMs (hardware key safes) and cloud key services take years to replace. Ask your vendors these questions now, and plan to replace hardware that cannot be upgraded.

Questions to ask every HSM, KMS and cloud key service vendor:

Question Why it matters
Which PQ algorithms are supported (ML-KEM, ML-DSA, SLH-DSA, LMS/XMSS), on which firmware or service versions, and from when? Hardware replacement cycles are long
Is the implementation FIPS 140-3 certified, or in the certification queue, with PQ algorithms included? Regulated environments need certified modules
How is the LMS/XMSS counter protected against rollback, cloning and backup restore? Reusing the counter breaks security
Can existing keys be re-wrapped, and is there an upgrade path without repeating the key ceremony? Operational cost
What are the performance and capacity figures for PQ signing and verification? ML-DSA signatures are bigger; throughput differs

Plan hardware replacement now for devices that cannot get firmware upgrades: root-CA HSMs, TPMs, smart cards and secure elements often last 10 to 15 years.

D.4Randomness matters more, not less

💡 In plain words

All crypto depends on good random numbers. Bad randomness breaks any algorithm, old or new. Use the operating system's random number generator, watch out for cloned virtual machines, and never reuse a nonce.

PQC schemes use randomness when making keys, when locking secrets, and (if hedged) when signing. Poor randomness causes total failure with any algorithm, and PQC gives no protection against that.

  • Use the operating system's secure random generator (CSPRNG) or a certified one (NIST SP 800-90A); never rely on rand(), timestamps or home-made generators.
  • Cloning a virtual machine or container can copy the random generator's internal state: make sure it gets fresh randomness after restoring a snapshot, and when embedded devices boot.
  • Never reuse a nonce (a "number used once") with AES-GCM or ChaCha20-Poly1305. This is unrelated to quantum, but it is still the most common real-world failure.
  • ML-DSA's hedged signing mixes fresh randomness with the key and message, which helps against hardware fault attacks; keep it on unless you have a specific reason to use deterministic mode.

D.5Implementation assurance

💡 In plain words

PQC is only as secure as the code that runs it. Use well-known libraries, look for official certification where you need it, test against standard test cases, and install side-channel fixes promptly.

  • Prefer well-maintained libraries (OpenSSL 3.5+, BoringSSL, AWS-LC, Go standard library, Bouncy Castle, wolfSSL, liboqs for prototypes). Some include ML-KEM code that has been mathematically proven correct or very heavily analysed.
  • Look for FIPS 140-3 (CMVP) certification and CAVP/ACVP algorithm validation for ML-KEM, ML-DSA and SLH-DSA where compliance requires it. Certifications are arriving gradually, so check NIST's current lists.
  • Run NIST ACVP and Project Wycheproof test cases in your own CI for any wrapper code you write.
  • Keep timing in mind: the 2023 KyberSlash issue showed that compiler or platform changes can make code take different amounts of time depending on secrets. Update promptly when libraries ship side-channel fixes.
  • For embedded devices and smart cards, ask about resistance to power analysis and fault injection (attacks that measure power use or deliberately disturb the chip), not only about basic correctness.

E.3Performance planning

💡 In plain words

The cost of PQ key exchange is about 2.3 KB of extra data per connection, not extra CPU. gRPC reuses connections, so it barely notices. Short-lived connections feel it most. When PQ certificates arrive, the extra data grows to 10 KB or more, which will matter more.

  • The cost is bytes, not CPU. A hybrid X25519MLKEM768 handshake adds about 2.3 KB in total compared with plain X25519 (about 1.2 KB each way). ML-KEM's maths takes tens of microseconds, similar to or faster than X25519.
  • gRPC spreads the cost. gRPC keeps HTTP/2 connections open for a long time and sends many calls over each one, so the handshake is paid once per connection, not per call. A service that keeps connections for hours barely notices. The pain shows up with short-lived connections: serverless functions, batch jobs opening many connections, mobile clients on poor networks, and health checks.
  • Reuse connections and resume sessions to cut the number of full handshakes. Tune keep-alive, connection pools and ticket lifetimes before blaming PQC.
  • Signatures change the picture. When PQ certificates arrive, handshakes will grow by roughly 10 KB or more, and QUIC's anti-amplification limit and TCP's initial sending window start to matter. Test with realistic chains early.
  • Large-scale estimate: extra outgoing data per day is roughly (full handshakes per day) × 2.3 KB. Even at 100 million handshakes per day that is a few hundred gigabytes, which is small next to application traffic for most services.

G.1Why Shor's algorithm works (the intuition)

💡 In plain words

Shor does not try every possible answer. It turns "find the factors" into "find the rhythm of a repeating pattern", and quantum computers are extremely good at spotting rhythms. Once you know the rhythm, the factors fall out with simple arithmetic.

Shor does not try every possible factor. It turns factoring into a period-finding problem (finding how often a pattern repeats), which quantum computers solve well using a tool called the quantum Fourier transform.

Tiny example, factoring N = 15:

diagram
Pick a = 7.  Look at the sequence 7^x mod 15:
  x=1: 7    x=2: 4    x=3: 13   x=4: 1   x=5: 7 ... it repeats every r = 4 steps (the period)

Because r is even: compute gcd(7^(r/2) - 1, 15) = gcd(48, 15) = 3
                          gcd(7^(r/2) + 1, 15) = gcd(50, 15) = 5
  -> 15 = 3 x 5

Reading the example: raise 7 to higher and higher powers and keep only the remainder after dividing by 15. The remainders go 7, 4, 13, 1, then repeat: a rhythm of length 4. Plug that rhythm into a simple greatest-common-divisor calculation and out pop 3 and 5, the factors of 15.

On a normal computer, finding the rhythm for a huge number is as hard as factoring it directly. A quantum computer puts many values of x into superposition at once, and interference makes the rhythm stand out when the result is measured. Like hearing a single note clearly when many instruments play together, because everything else cancels out. The same trick, applied to the structure of elliptic curves, breaks elliptic-curve crypto. This is why all RSA, DH and ECC variants fall together, and why the fix has to be different maths, not bigger numbers.

G.2Security terms you will see in standards

💡 In plain words

G.3PQC, QKD and quantum random numbers: what is what

💡 In plain words

Three things with "quantum" in the name get confused. PQC is software and is the real solution. QKD is special physics hardware for niche cases. Quantum random number generators are just a source of randomness, not a fix.

Appendix H · HNDL deep dive

Harvest Now, Decrypt Later (HNDL) in depth

10 pages · 0 read

Section 2.5 introduced HNDL. This appendix turns it into something you can assess and act on: who can record your traffic, what exactly can be recorded and broken later, how to rank your own data, which defences work and which popular ideas do not.

H.1The attack, step by step

💡 In plain words

Today, the attacker quietly copies your encrypted traffic and stores it. Years later, with a quantum computer, they break the key exchange at the start of each recording and read everything. You never get an alert, and fixing things later does not help what was already recorded.

diagram
Today                                                     Future (CRQC exists)
 1. Victim connects (TLS, VPN, SSH, Wi-Fi, messaging)       4. Attacker runs Shor on the recorded
 2. Attacker passively records packets:                        key exchange public values
      handshake (public key shares) + encrypted data        5. Recovers the session keys
 3. Attacker stores them (cheap, silent)                    6. Decrypts the stored data

What makes it dangerous:

  • Silent and undetectable. Copying packets leaves no trace on your systems. You will never get an alert.
  • Nothing has to be broken today. The attacker only needs storage and patience.
  • Works backwards in time. A fix you deploy in 2030 does nothing for traffic recorded in 2026.
  • The attacker needs both parts: the handshake (to break the key exchange) and the encrypted data (to read). Either one alone is useless.

H.2Who can realistically record, and where

💡 In plain words

Anyone who can sit on the path between you and the other end can record: intelligence agencies on backbone cables, internet providers, public Wi-Fi, a compromised switch, or a hacker who steals your packet captures. Recording everything is expensive, so attackers target high-value organisations and links.

Vantage point Examples Notes
Internet backbone and exchange point taps Intelligence agencies, large carriers under legal orders Selective but large-scale; undersea cables and transit links are classic targets
Internet provider and mobile networks Compromised or legally compelled providers Home and mobile traffic of many users
Hostile or shared local networks Public Wi-Fi, hotel and conference networks, hacked routers Opportunistic recording
Cloud and datacentre networks A compromised switch, a rogue insider, a misconfigured mirror port Internal traffic is usually less exposed, but not immune
Partner and site-to-site links Leased lines, VPNs between companies High-value, long-lived traffic
Hacked endpoints and proxies A breached sidecar, load balancer, or a monitoring system that stores packet captures Stolen packet captures (PCAPs) count as harvesting
Stolen storage Stolen database dumps, backups, cloud storage The same idea, often called "steal now, decrypt later" (see H.5)

How much can one attacker store? A fully loaded 1 Gbps link produces about 10.8 TB per day, so recording everything is expensive and real-world harvesting is targeted at high-value organisations, links and data. But storage gets cheaper every year, and an attacker planning ten years ahead may happily pay. Assume that valuable data crossing the public internet or someone else's network can be recorded.

H.3What can be recorded and broken later, and what cannot

💡 In plain words

If the key was agreed using RSA, DH or elliptic curves, the recording can be broken later. If it used a hybrid quantum-safe exchange, or a strong pre-shared secret, or the data is protected only by AES-256 with a key that never travels, it is safe.

Traffic or data Breakable later? Why
TLS 1.2 or 1.3 with X25519, P-256 and similar (classical) Yes The temporary key exchange falls to Shor, revealing the session keys
TLS 1.2 with static RSA key exchange Yes, and worse Recorded sessions fall to RSA being broken, and also to any future theft of the server's key
TLS 1.3 with hybrid X25519MLKEM768 No (needs both X25519 and ML-KEM broken) Hybrid protects the key exchange
SSH with curve25519 only Yes Classical key exchange
SSH with mlkem768x25519-sha256 No Hybrid
IPsec or WireGuard with classical Diffie-Hellman only Yes Everything inside the tunnel
IPsec or WireGuard with a strong pre-shared key mixed in No (the pre-shared key is a symmetric secret the attacker does not have) Works as a quantum-resistant layer
Wi-Fi WPA3 SAE, Bluetooth pairing, 5G identity hiding Yes (classical ECC) Short-range, but can be recorded
Signal PQXDH and SPQR, iMessage PQ3 Largely no Post-quantum key agreement and ratcheting already added
Files or archives encrypted to an RSA or ECC public key (PGP, S/MIME, ECIES) Yes The wrapped file key falls to Shor
Stored data encrypted with AES-256, key kept in KMS or HSM and never sent using classical crypto No Symmetric only
Hashes (SHA-256, SHA-3) and HMAC No Grover only halves the strength

H.4Does TLS 1.3 forward secrecy protect me? (A common misunderstanding)

💡 In plain words

No. Forward secrecy protects you if someone steals the server's long-term key later. It does not protect you if someone breaks the temporary key exchange itself, which is exactly what a quantum computer does.

Forward secrecy defends against someone stealing the server's long-term key later. It does not defend against breaking the temporary key exchange itself, which is exactly what Shor does to X25519 and P-256. So a perfectly configured classical TLS 1.3 connection with forward secrecy can still be harvested. The only fixes are a quantum-safe key exchange (hybrid or PQ) or an extra symmetric secret.

H.5Variants you should know

💡 In plain words

Besides recording network traffic, attackers can steal stored data now to decrypt later, or rely on old signatures becoming forgeable. The signature version only matters for things that must stay trustworthy for years.

Name Meaning Example
HNDL (harvest now, decrypt later) Record encrypted traffic now, decrypt once a quantum computer exists Recorded TLS, VPN and SSH sessions
SNDL (steal now, decrypt later) Steal encrypted stored data or backups now, decrypt later A stolen backup whose data key is wrapped with RSA, or a database dump with RSA-wrapped data keys
Trust now, forge later (sometimes "harvest now, forge later") Signatures made today can be faked after a quantum computer exists, if the checker cannot tell when they were really made Contracts, audit logs, software releases and firmware signed with RSA or ECDSA and checked years later; defended by trusted timestamps, evidence records, re-signing and PQ signatures

The signature version differs in one important way: live identity checks (a TLS handshake) can only be faked by someone who already has a quantum computer at that moment, so they cannot be attacked backwards in time. Stored, long-lived signed items are where future forgery matters.

H.6Scoring your own data: the HNDL assessment

💡 In plain words

For each type of data, ask how long it must stay secret, how long fixing it will take, how exposed it is, how valuable it is to a patient attacker, and whether it relies on old public-key crypto. Then use Mosca's rule from 2.6 to see if you are already late. For most enterprise data, you are.

For each data flow or store, answer five questions:

Question Typical answers
1. How long must this stay secret? (X) Minutes (session tokens), 1 to 7 years (payment data), 10 to 30 years (health, legal, intellectual property), 50+ years (classified, genetic)
2. How long will it take to protect it? (Y) Include vendor dependencies and hardware replacement
3. How exposed is the network path? Public internet, someone else's network, private link, same machine
4. How valuable is it to an attacker with long-term resources? Nation-state interest, competitor interest, criminal resale value
5. Is there a classical public-key step anywhere? Key exchange, key wrapping, PGP, ECIES, classical VPN

Then apply Mosca's inequality: you are late if X + Y > Z, where Z is the number of years until a quantum computer can break crypto. Nobody knows Z, so try several values:

Data X (years secret) Y (years to migrate) X + Y Late if Z is less than
Session cookies, one-time codes under 1 1 about 1 Effectively never
Card data and transaction logs 7 3 10 10 years
Company strategy, merger and acquisition material 15 4 19 19 years
Source code, trade secrets, R&D 20 4 24 24 years
Patient records 30 5 35 35 years
Government and defence secrets, genetic data 50 or more 7 57 or more 57 years

If you think Z could plausibly be 10 to 15 years, then everything with X + Y above 15 needs action now. That covers a large share of enterprise data.

A simple score to order the work: (how exposed the link is) × (how valuable the data is to a patient attacker) × (years it must stay secret), for flows that rely on classical key exchange. Fix the highest scores first. These are usually partner VPNs, internet-facing APIs carrying sensitive data, remote administration (SSH) and bulk data transfers.

H.7The HNDL exposure map for a typical gRPC platform

💡 In plain words

On a typical platform, the public internet link and partner links come first, then cross-region links, admin access and backups, and only then the internal hops inside a cluster.

Hop Chance of being recorded Priority
Mobile or browser to the edge load balancer (public internet) High First
Partner API links and site-to-site VPNs High, and high value First
Cross-region and cross-cloud links (even on a provider's own network) Medium High
Remote administration (SSH, kubectl, database consoles) Medium, and carries secrets High
Edge to service-mesh ingress, and service-to-service inside a cluster Lower, but insider or compromise risk Medium, after the edge
Same-machine loopback (app to sidecar) Very low Low
Backup and replication traffic leaving the datacentre Medium to high High

H.8The mitigation ladder

💡 In plain words

Seven defences, best first: don't keep data you don't need; switch to hybrid key exchange; add pre-shared secrets where hybrid isn't available yet; wrap old traffic in a quantum-safe tunnel; encrypt the most sensitive data inside the app too; re-encrypt old archives; and measure that it's all working. Nothing can protect traffic that was already recorded.

Start at the top; each step is cheaper or stronger than the next.

Step Action Effect on HNDL
1 Do not send or keep it. Collect less, keep it for less time, replace it with tokens or delete it once its purpose is over Removes the target entirely
2 Hybrid post-quantum key exchange on every protocol in scope (TLS, SSH, IPsec, application-level HPKE) Closes the recording window for new traffic
3 Quantum-resistant symmetric layer: 256-bit pre-shared keys in VPNs and TLS PSK modes, AES-256 keys kept in HSM and KMS Closes it immediately where hybrid is not yet available
4 Layered tunnels: a PQ-protected tunnel around classical traffic A passive listener on that stretch of the path sees only PQ-protected data (protection ends where the tunnel ends)
5 Application-level encryption with ML-KEM or hybrid HPKE plus AES-256-GCM for the most sensitive data Protects even if the lower layers are classical
6 Re-encrypt stored archives and re-wrap data keys that relied on RSA or ECC Fixes stored data that could still be stolen (SNDL)
7 Measure: dashboards of hybrid usage per hop; alerts when connections fall back to classical-only Proves the window is closed

Important limit: nothing you do now can protect data that was already recorded using classical key exchange. For that data, the only options are to assume it will be exposed some day, and to make sure its value runs out before then (change credentials, change secrets, update plans, re-key relationships).

H.9What does not help against HNDL

💡 In plain words

Bigger keys, forward secrecy, frequent certificate changes, PQ certificates on their own, AES-256 on its own, disk encryption and waiting: none of these stop recorded traffic from being decrypted later.

Idea Why it fails
Bigger RSA or ECC keys Shor copes easily with bigger keys; only a little more quantum effort
TLS 1.3 forward secrecy alone It protects against key theft, not against a quantum break of the temporary key exchange
Changing certificates often Certificates prove identity; they do not protect the secrecy of recorded key exchanges
Post-quantum certificates alone Signatures do not do key exchange; HNDL is about key exchange
AES-256 alone with a classical key exchange The AES key comes from the key exchange: break that and AES-256 does not matter
Disk encryption Protects stolen devices, not recorded network traffic
Waiting until quantum computers appear By then, everything recorded in the meantime is exposed

H.10One-paragraph summary

HNDL is a threat to secrecy that exists today, because attackers can cheaply store encrypted traffic and decrypt it once a quantum computer arrives. It affects any session whose key was agreed using RSA, DH or elliptic curves, and any file whose key was wrapped with them. The fix is a post-quantum or hybrid key exchange (or a strong symmetric secret) on every path that carries long-lived sensitive data, starting with internet-facing, partner and remote-access links. Signatures matter later, mostly for long-lived keys and stored signed items. The sooner you switch a path, the less recorded data stays exposed.

The eBPF Sketchbook

eBPF lets you slip tiny, safe programs into the heart of a running Linux computer, the kernel, to watch it, measure it and protect it. No reboot. No risk of crashing it.

In kid words: the kernel is a castle that runs your computer. eBPF programs are little helper bees. A strict guard checks every bee before it may fly in. Inside, bees watch the doors and leave notes in honey jars for you.

eBPF is an in-kernel virtual machine. You load sandboxed bytecode with the bpf() system call; the verifier proves it is safe, a JIT compiles it to native code, and it runs every time the hook it is attached to fires. It shares data with user space through maps.

Chapter 1

The whole idea in six pictures

Read it like a comic strip. Everything in it moves a little.

  1. Meet the kernel. Every computer has a boss program called the kernel. Think of it as a castle that controls everything: the screen, the files, the internet, and whose turn it is to use the processor.

  2. Apps live outside. Your browser and games can't touch the hardware themselves. They knock on the castle window and ask. That knock is called a system call.

  3. Changing the castle is hard. Adding a new rule to the kernel can take years. The shortcut, a kernel module, is risky: one wrong brick and the whole castle falls down.

  4. Send in the bees! eBPF lets you write tiny programs (our bees) and send them into the castle while it keeps running. No rebuilding. No restarting.

  5. The guard checks every bee. Before a bee goes in, a strict guard called the verifier makes sure it can't break anything and will always come back. Unsafe bees are turned away.

  6. Bees watch and report. Inside, bees sit at doors and windows. They count visitors, stop troublemakers and drop notes into honey jars (called maps) that your apps can read.

The same story, in kernel words. Apps run in user space and enter the kernel through system calls such as openat() or execve(). New kernel behaviour used to mean a kernel patch (merged upstream, then shipped by distributions years later) or a loadable kernel module (full privileges, no safety net). eBPF adds a third option: verified, sandboxed programs loaded at runtime and attached to events.
Chapter 2

Why not just change the kernel?

Say you want the kernel to do something new, like count every network packet or block a sneaky program. There are three ways to do it. Let's race them.

Change the kernel itselfWrite a kernel moduleWrite an eBPF program
How long until I can use it?Years (review, release, then every distro)MinutesSeconds
Can a bug crash the computer?YesYes, very easilyNo. The verifier blocks unsafe code
Need to reboot?YesNoNo
Works on other kernel versions?Only newer onesMust rebuild for each kernelUsually yes (with CO-RE)
Who can do it?Kernel developersBrave expertsAnyone with admin rights

Kernel modules run with full kernel privileges and no checks: one null-pointer dereference means a kernel panic, and they are tied to the exact kernel build. eBPF programs are verified before loading, can only call approved helpers, and with BTF plus CO-RE (Compile Once, Run Everywhere) one binary adapts to many kernel versions. A popular way to put it: eBPF does to the kernel what JavaScript did to web pages.

      Chapter 4
      
The verifier: the strictest guard in town

      
Before any eBPF program runs, the verifier reads it and imagines every possible way it could run. If even one path could hurt the kernel, the whole program is turned away. These are its rules.

    

    
    
      
  • It must finish
    No endless loops. A bee that never comes back would freeze the castle.
    The control-flow graph must reach exit. Loops are allowed only when the verifier can prove they end (bounded loops since Linux 5.3, plus helpers like bpf_loop()).
    • 
      
  • Don't touch what isn't yours
    A program may only read and write memory it was given, and never past the end.
    Every register has a tracked type (context, packet, map value, stack…) and a min/max range. Each load and store is checked against those bounds.
    • 
      
  • Check before you open
    Looking something up in a map might find nothing. You must check before using it.
    bpf_map_lookup_elem() returns PTR_TO_MAP_VALUE_OR_NULL. Dereferencing it before a NULL check is rejected.
    • 
      
  • No reading empty drawers
    You can't read a box you never filled. It might hold leftover secrets.
    Reading uninitialised registers or stack slots is rejected, so kernel memory can't leak out.
    • 
      
  • A small backpack
    Each program gets only 512 bytes of scratch space. Big data goes into maps.
    The BPF stack is 512 bytes, addressed from the read-only frame pointer R10.
    • 
      
  • Only approved tools
    Programs can only call kernel functions from an approved toolbox, and only with the right kinds of things.
    Allowed helpers and kfuncs depend on the program type; argument types are checked, and some helpers need a GPL-compatible license.
    • 
      
  • Easy enough to check
    The guard will look at up to one million steps. Programs that are too twisty are sent back.
    The complexity limit is 1,000,000 processed instructions. State pruning skips paths it has already proven safe.
    • 
      
  • Leave properly
    Every path must end with a clear answer, like "let this packet pass".
    R0 must hold a valid return value at exit, and the value must make sense for the program type.
    •

    After the guard says yes
    
        
    A JIT compiler translates the program into the CPU's own language so it runs at full speed. Then the program's memory is locked so nobody can change it.
    
        
    The JIT emits native x86-64, arm64, riscv64 (and more) code. The image is made read-only, constants can be blinded to resist JIT spraying, and Spectre mitigations are applied.
    
      
    
      
    
        
    Who may load programs?
    
        
    Only trusted users, like an administrator. Ordinary apps can't sneak bees into the castle.
    
        
    Loading usually needs CAP_BPF plus CAP_PERFMON or CAP_NET_ADMIN (or root). Unprivileged BPF is disabled by default on most distributions via kernel.unprivileged_bpf_disabled.
    
      
    
    
    
  
    

    



    
  
    
    
    
      Chapter 5
      
    Inside the tiny eBPF computer
    
      
    eBPF programs don't run as the C you write. They're turned into bytecode: instructions for a tiny made-up computer with 11 registers (think of them as 11 hands that can each hold one number) and a 512-byte backpack called the stack.       Anatomy of one instruction
      
      
      Every eBPF instruction is exactly 64 bits. Here's r1 += r2 taken apart:
      
      
      
        
      0x0fopcode · 8 bits
      "add, 64-bit, register"
      
        
      1dst · 4
      r1
      
        
      2src · 4
      r2
      
        
      0offset · 16 bits
      used by jumps & memory
      
        
      0immediate · 32 bits
      a constant number
      
      
      
      
      Register conventions: R0 holds return values, R1–R5 pass arguments to helpers (R1 starts as the context pointer), R6–R9 survive helper calls, and R10 is the read-only frame pointer. The instruction set is standardised in RFC 9669. Run bpftool prog dump xlated id <N> to see a loaded program's bytecode, or dump jited for the machine code.

      Chapter 7
      
      Maps: the honey jars
      
      
      A bee forgets everything when its job is done. To remember things, or to pass notes to your app outside the castle, it puts them in a map. There are different jars for different jobs.
      
    
      
    
        
    
        
      
        
        
        Watch a ring buffer
        
        
        A ring buffer is a merry-go-round of slots. The kernel bee drops events in on one side. Your app picks them up on the other, in order. If the app is too slow and the ring fills up, new events are dropped. Try it.
        
        
        
        
        
          
        0written
        
          
        0read
        
          
        0dropped
        
          
        0/16in the ring
        
        
        
        
        BPF_MAP_TYPE_RINGBUF (Linux 5.8) is one buffer shared by all CPUs, keeps events in order, and lets the program reserve space then submit. User space polls it through an epoll-able file descriptor; libbpf wraps this as ring_buffer__poll().

      Chapter 11
      
            How we got here
            
      
            eBPF grew out of a small packet filter from 1992. Scroll along the road.
            
    
            
    
            
      
              
        
            1. 1992
              BPF is born
              Steven McCanne and Van Jacobson describe the BSD Packet Filter. tcpdump uses it to pick which packets to show.
              2. 
        
            2. 1997
              Linux gets BPF
              Linux 2.1.75 adds the socket filter, BPF's first home in Linux.
              3. 
        
            3. 2011
              Made fast
              A JIT compiler turns classic BPF into native machine code (Linux 3.0).
              4. 
        
            4. 2012
              seccomp-bpf
              Programs like Chrome use BPF filters to limit which system calls they may make (Linux 3.5).
              5. 
        
            5. 2014
              eBPF arrives
              Alexei Starovoitov's extended BPF lands, and Linux 3.18 adds the bpf() system call.
              6. 
        
            6. 2015
              Tracing superpowers
              eBPF can attach to kprobes (Linux 4.1). The BCC toolkit appears.
              7. 
        
            7. 2016
              XDP
              eXpress Data Path lets eBPF handle packets right in the driver (Linux 4.8).
              8. 
        
            8. 2018
              BTF & bpftrace
              BPF Type Format arrives (Linux 4.18) and bpftrace makes one-liners easy.
              9. 
        
            9. 2019
              Loops & CO-RE
              The verifier accepts bounded loops (Linux 5.3). CO-RE: compile once, run everywhere.
              10. 
        
            10. 2020
              Security & rings
              LSM programs can enforce security rules (5.7). The ring buffer map arrives (5.8).
              11. 
        
            11. 2021
              Going big
              The eBPF Foundation forms under the Linux Foundation. Microsoft announces eBPF for Windows.
              12. 
        
            12. 2023
              Cilium graduates
              The eBPF-based networking project becomes a graduated CNCF project.
              13. 
        
            13. 2024
              Schedulers & a standard
              sched_ext lets eBPF decide who gets the CPU (Linux 6.12). RFC 9669 standardises the instruction set.
              14. 
        
            14. Now
              Everywhere
              From Android phones to the biggest clouds, eBPF quietly watches, routes and protects.

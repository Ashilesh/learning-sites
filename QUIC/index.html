QUIC

A newer, faster way for your phone or laptop to talk to websites. It keeps working when your network changes, and it locks every message by default.

For curious people, students and junior developers. No networking background needed. We'll explain everything with one picture: sending parcels by courier.

TCP: the careful registered-post courier

TCP (1981) guarantees every parcel arrives, in the right order. It has carried most web traffic for over 40 years.

  • It phones ahead first (the handshake). "Hello, are you there?" → "Yes, I'm here" → "Great, starting now." One full round trip before any real data moves.
  • Then a second chat for the lock (TLS). Both sides agree on keys. With TLS 1.3 that costs another round trip; older TLS cost two.
  • Every parcel is numbered and signed for. If parcel 5 goes missing, the sender re-sends it.
  • Strict order. Parcels 6, 7 and 8 wait until parcel 5 arrives. This is called head-of-line blocking.
  • Tied to your address. Change from Wi‑Fi to mobile data, your IP address changes, and the connection breaks and starts over.

Why that matters

A web page is many files: HTML, CSS, images, scripts. HTTP/2 sends them all down one TCP connection.

On a perfect network that's efficient. On a lossy mobile network, one lost packet freezes all of them.

The supermarket with one till

One till, one queue. Each shopper carries one file of your web page. If the person at the front can't find their wallet, everyone behind waits, even people buying one item.

UDP: the postcard (and why QUIC is built on it)

UDP (1980) is the simplest courier on the internet. It writes an address on a postcard and drops it in the post box. No phone call first, no tracking, no re-sending, no ordering.

What a UDP packet carries, drawn to scale

The UDP header is only 8 bytes: four fields of 2 bytes each. TCP's header is at least 20 bytes and comes with a whole tracking system around it.

What UDP does NOT do

  • No handshake. It just sends.
  • No guarantee of delivery. A lost postcard is simply gone.
  • No order. Postcard 3 may arrive before postcard 1.
  • No speed control. It doesn't slow down when the network is crowded.
  • No encryption. Anyone handling it can read it.

Why would anyone want that?

Because sometimes late is worse than lost.

  • Live video call: a frame from half a second ago is useless now. Skip it and show the current one.
  • Online games: where a player is right now matters more than 200 ms ago.
  • DNS: one tiny question, one tiny answer. A full handshake would take longer than the question.
Video call over postcards

Each postcard is one video frame. Some get lost, some overtake others. The call never waits: an old frame that turns up late is thrown away.

Why QUIC is built on top of UDP

1. Only two couriers get through. Routers, firewalls and home Wi‑Fi boxes understand TCP and UDP. A brand-new protocol would be blocked. This is called ossification: the network has set like concrete.

2. TCP lives inside the operating system. Changing it means updating Windows, Android, iOS and Linux on billions of devices. That takes decades.

3. UDP is a blank postcard. It adds almost nothing, so QUIC can write its own rules inside it: numbering, re-sending, per-stream order, speed control and encryption.

4. QUIC ships inside the app. Google, Mozilla or Apple can improve it with a normal browser update.

The picture to keep

UDP is a plain envelope that every post office accepts. QUIC puts a smart, locked, tracked package system inside that envelope. Post offices just see an ordinary envelope and let it through.

So what is QUIC?

QUIC is a transport protocol that does TCP's job (reliable, ordered delivery) plus TLS's job (encryption) in one layer, carried inside UDP packets.

2012

Google starts experimenting with QUIC in Chrome and its own servers.

2016

The IETF, the body that standardises internet protocols, takes it over and redesigns it.

May 2021

QUIC becomes an official standard: RFC 9000.

June 2022

HTTP/3, the web on QUIC, is published as RFC 9114.

Today

About 41% of websites support HTTP/3 (W3Techs, Nov 2026). All major browsers do.

About the name: it started as "Quick UDP Internet Connections". The standard now treats QUIC as just a name, not an acronym.

QUIC's five big ideas

1

Faster start

The hello and the lock happen in one conversation, not two.

2

Many lanes

Each file gets its own stream, so one lost packet only delays its own file.

3

Survives moves

Connections wear an ID badge, so switching Wi‑Fi to mobile doesn't break them.

4

Always locked

There is no unencrypted QUIC. Even most control info is hidden.

5

Lives in the app

Improved by updating the browser or server, not the operating system.

QUIC and HTTP/3

QUIC is the courier. HTTP/3 is the language the web page is written in when it travels with that courier.

HTTP/1.1 and HTTP/2 use TCP. HTTP/3 uses QUIC.

How QUIC works, one idea at a time

Each card shows a problem. Flip it to see QUIC's fix and an everyday example.

idea 1

The combined handshake

Problem: TCP + TLS 1.3 needs two round trips (hello, then lock) before the first byte of a web page.

flip ↻
QUIC fix · 1 round trip

The hello and the TLS 1.3 key exchange travel in the same first packets. One round trip and the connection is ready and encrypted.

Like: instead of calling a restaurant to check it's open, then calling again to order, you ring once: "Are you open? I'd like a pizza."

↺
idea 2

0-RTT resumption

Problem: even one round trip is slow on a far-away or mobile connection (100–300 ms each).

flip ↻
QUIC fix · zero round trips

If you've talked to this server before, your device keeps a ticket. Next time it sends the request with the first packet.

Like: a regular at the café. The barista starts the usual coffee before they say a word.

Careful: an attacker can replay 0-RTT data, so it's only safe for harmless requests like loading a page, never "transfer money".

↺
idea 3

Streams

Problem: in TCP, one lost packet freezes every file on the connection.

flip ↻
QUIC fix · no more head-of-line blocking

One connection carries many independent streams. A lost packet for the image delays only the image; text and CSS keep flowing.

Like: a supermarket with many tills. A slow shopper only holds up their own queue.

↺
idea 4

Connection IDs

Problem: TCP knows you by IP address and port. Phone hops from Wi‑Fi to 5G, address changes, download breaks.

flip ↻
QUIC fix · connection migration

Each connection has a connection ID, like a tracking number. The server recognises it from a new address and the transfer continues.

Like: you move house mid-subscription. The magazine still finds you, because it's tied to your subscriber number, not your street.

↺
idea 5

Smarter loss recovery

Problem: TCP re-sends a packet with the same number, so it can't tell which copy got the reply. Its timing gets muddled.

flip ↻
QUIC fix · fresh numbers

Every packet gets a new, ever-increasing number, even re-sends. Acks also say how long the receiver held the packet, so the sender measures the network better.

Like: re-sending a lost letter with a new reference number, so you know which letter the reply is about.

↺
idea 6

Encryption built in

Problem: in TCP, TLS is optional and sits on top. TCP's own headers stay visible and can be tampered with.

flip ↻
QUIC fix · always on

The payload and most control info (packet numbers, acks) are encrypted. Only a small part of the header stays readable.

Like: sealing the parcel and the delivery notes in a locked box. The courier only sees the address label.

↺
idea 7

Congestion control in the app

Problem: improving TCP's speed rules needs operating-system updates.

flip ↻
QUIC fix · upgradeable

QUIC still slows down when the network is busy, like TCP. But the algorithm (such as Cubic or BBR) lives in the app, so it can be tuned and upgraded quickly.

Example: loading the news on a train

Priya opens a news site on her phone as her train leaves the station. The page has a headline, text, a stylesheet and 10 photos. Halfway through, her phone switches from station Wi‑Fi to 4G, and the 4G drops a few packets in a tunnel.

Times are simulated with a 0.3 s round trip. Watch what freezes and what keeps going.

With TCP + TLS (HTTP/2)

  1. Two round trips of setup before the first byte.
  2. A packet from photo 3 is lost in a tunnel. Text and other photos already received are held back until it's re-sent. The whole page stalls.
  3. The phone moves to 4G. Her IP address changes, the connection dies, and the browser starts over with a fresh handshake.

With QUIC (HTTP/3)

  1. One round trip of setup, or zero if she read this site yesterday.
  2. The packet from photo 3 is lost. Only photo 3 waits; headline, text and other photos keep appearing.
  3. The phone moves to 4G. The server recognises the connection ID from the new address and the download carries on.

Limitations: why not everyone uses QUIC yet

About 41% of websites offer HTTP/3, so most of the web still runs on TCP. Support is lopsided: big CDNs switch it on by default, while self-hosted servers often don't.

All websites41%
On Cloudflare87%
On Nginx13.5%

The hotel Wi‑Fi gate

Many company, hotel and public networks only let web traffic through on TCP port 443. Watch what the browser does.

The browser tries QUIC first and keeps TCP ready as a backup.

UDP gets blocked or throttled

Many firewalls, hotel and public Wi‑Fi only allow web traffic over TCP port 443, or slow UDP down because it was used in attacks. The browser falls back to TCP.

hurts: users on corporate & public networks

Higher CPU cost

TCP's work is done by the operating system and network card, tuned for decades. QUIC does encryption and packet handling in app code, packet by packet, so servers can use noticeably more CPU.

hurts: server operators, data-centre bills

Harder to see inside

Almost everything is encrypted, so firewalls, load balancers and monitoring tools can't read packet numbers or delays like they can with TCP.

hurts: enterprises, ISPs, security teams

Small gains on good networks

On fast, stable fibre with almost no loss, HTTP/2 over TCP already does well. The big wins are on mobile and lossy links.

hurts: sites with mostly desktop broadband users

Young server support

Popular servers and libraries added QUIC late, and some features are still experimental. Many companies wait for "boring and stable".

hurts: self-hosted sites, smaller teams

Discovery costs a trip

A browser usually learns a site speaks HTTP/3 only after a first visit over TCP (via the Alt-Svc header). The first visit doesn't benefit.

hurts: first-time visitors

Load balancing is harder

Load balancers route by IP and port. With migration the address can change, so they must route by connection ID, which needs new software.

hurts: large server fleets

0-RTT replay risk

Data in a 0-RTT first packet can be captured and re-sent by an attacker. It's only safe for requests that are harmless to repeat.

hurts: app developers

OS & hardware gap

Operating systems were built around TCP. UDP batching (GSO/GRO) helps, but QUIC lacks TCP's decades of hardware offload.

hurts: high-traffic servers
In one line

QUIC is faster where networks are messy, but it costs more CPU, is harder to inspect, and some networks still block it. So many organisations stick with TCP for now.

How the limitations can be overcome

Most of QUIC's limits are about missing support and tooling, not flaws in the design. Each one has a practical fix. Flip each card between problem and fix.

Own a small website?

The easiest path: put the site behind a CDN that offers HTTP/3 and switch it on. Visitors whose network blocks UDP automatically fall back to HTTP/2, so nothing breaks.

Glossary stick these on your fridge

Packet

A small chunk of data sent across the network.

Round trip (RTT)

The time for a message to go to the server and a reply to come back.

Handshake

The setup conversation before real data is sent.

TLS

The security layer that encrypts data. The padlock in your browser.

Stream

One independent lane of data inside a QUIC connection.

Head-of-line blocking

When one missing piece holds up everything behind it.

Connection ID

QUIC's tracking number for a connection, independent of your network address.

0-RTT

Sending data in the very first packet to a server you've visited before.

Ossification

The internet's middle boxes being so set in their ways that new protocols get blocked.

HTTP/3

The version of the web's language that runs on QUIC.
